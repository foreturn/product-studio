# 架构决策

- 产品标识：`product-studio`
- 关联功能规格：`docs/product/product-studio/feature-spec.md`
- 决策状态：已接受

## 背景

插件需要在 Claude Code 与 Codex 中共享同一套产品开发行为，同时把提示词稀疏的输入扩展为可实施契约。若扩写、实现和验收混在单一 Skill 中，角色会互相越权；若为每个动作继续拆分新 Skill，又会增加触发冲突和上下文成本。

## 受影响边界

- 共享行为内核：`skills/*/SKILL.md`、各 Skill 引用的原则文档与 `templates/`。
- Codex 适配层：`.codex-plugin/plugin.json` 与 `skills/*/agents/openai.yaml`。
- Claude Code 适配层：`.claude-plugin/plugin.json`。
- 持久化协作层：目标仓库中的 `docs/product/<product-slug>/`。
- 质量门禁：`scripts/validate_project.py` 及双端各自的 manifest 校验器。

## 不变量与失败模式

### 不变量

- 用户原始意图始终保留，扩写内容不能冒充用户确认事实。
- 产品范围与验收标准只有产品角色可以主责修改；专项角色发现偏差时必须退回。
- 重要架构不变量只有架构角色主责记录；实现角色不能静默绕过。
- 验收结论必须逐项引用当前证据，构建通过不等同于产品通过。
- 双端共享 Skill 不依赖任一平台专属工具名。
- 流程可从持久化产物恢复，不以对话历史作为唯一状态源。

### 失败模式

- 过度联想：代理把偏好猜测写成确认需求，导致实现方向偏离。
- 过度追问：代理把可从仓库查明或可逆的细节全部抛给用户，破坏氛围编程体验。
- 角色越权：前端、后端或验收角色静默改变范围以便完成自身任务。
- 文档仪式化：生成全部模板却没有真实输入或下游消费者。
- 假闭环：只运行静态校验或构建便宣称完整用户旅程已经交付。
- 交付断点：验收后没有发布授权、回滚、运行验证与反馈回流，无法证明产品在目标环境产生预期结果。
- 双端漂移：Codex 与 Claude manifest 或共享 Skill 行为产生不一致。

## 候选方案

### 方案一：新增独立的提示词扩写 Skill

优点是触发词明确；缺点是会把用户、价值、范围与验收等产品职责拆出产品角色，形成两份需求真相，并增加编排和触发冲突。

### 方案二：强化产品角色，由交付角色编排（采用）

`product-discovery` 唯一负责证据化扩写与产品契约；`product-delivery` 负责分类、阶段推进、退回与收口；其余角色各守专项边界。既沿用现有六 Skill，也让扩写自然落在产品生命周期起点。

### 方案三：合并为一个全能 Skill

触发简单，但上下文庞大、职责混杂，难以支持局部任务，也无法阻止同一角色自行改需求并自行验收。

## 最终决策

采用“一个编排角色、六个专项角色、持久化契约交接、平台薄适配”的结构：

```text
原始短提示词
      |
      v
product-delivery  接入、分类、阶段状态、变更控制
      |
      v
product-discovery  证据化扩写、范围、验收标准
      |
      +--> system-design（跨边界风险存在时）
      |
      +--> frontend-experience（有用户可见行为时）
      |
      +--> backend-contract（有服务端或数据行为时）
      |
      v
delivery-verification  逐项追溯、失败路径、回归、交付结论
      |
      v
release-operations（适用且获授权时） 发布、运行验证、回滚、反馈
      |
      `-----------------------------> product-discovery
```

每个 Skill 统一包含：角色定位、输入契约、职责、执行流程、输出契约、交接门禁与边界。编排只选择当前任务所需的最小角色链路，不强制生成无消费者的文档；实际发布必须由明确授权开启。

## 后果与权衡

- 优点：角色边界清楚，短提示词扩写有唯一所有者，单项任务与端到端任务均可复用。
- 优点：持久化契约让会话中断、角色切换和验收追溯更可靠。
- 优点：共享内核与薄适配降低 Claude Code、Codex 双端漂移。
- 优点：发布后的技术、业务与用户反馈能回到产品角色，形成真正的迭代闭环。
- 代价：Skill 指令和模板比原先更严格，需要静态校验防止章节退化。
- 代价：真实减少返工的效果仍需安装后前向测试，静态校验只能证明结构契约存在。

## 迁移与回滚

- 保留六个既有 Skill 的名称与目录，新增 `release-operations`，现有显式调用无需迁移。
- 先更新共享 Skill 和模板，再同步双端描述与 Codex UI 元数据。
- 不修改已安装插件缓存；源码验证完成后再由用户决定安装时机。
- 若新流程造成不必要的文档负担，可保留角色契约，仅缩减非必需产物；不得移除原始意图、假设分级与验收追溯。

## 验证边界

- 静态验证：角色集合、统一章节、模板引用、双端 manifest 共享字段、无占位符。
- 平台验证：Codex manifest 校验与 Claude Code plugin validate。
- 行为走查：短提示词、局部前端、局部后端、独立验收四种入口的最小路由与门禁。
- 发布走查：区分方案与执行授权，验证制品追溯、技术与业务信号、回滚和反馈回流。
- 暂不验证：安装后模型触发准确率、用户交互轮数与真实返工率；这些需要后续独立前向测试。
