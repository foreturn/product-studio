# 产品简报

- 产品标识：`product-studio`
- 决策状态：按已记录假设继续

## 原始意图

为 Claude Code 与 Codex 提供一套面向氛围编程的产品开发插件。用户通常只给出很短的提示词，插件需要结合仓库证据补全意图、显式约定边界，并由职责清晰的角色完成产品开发全生命周期闭环，以减少方向偏差、遗漏状态和交接返工。

## 背景

- 产品或功能：跨 Claude Code 与 Codex 的产品研发工作流插件。
- 目标用户：使用编码代理完成产品或功能、但不愿先写完整需求文档的个人开发者与小团队。
- 用户问题：短提示词缺少用户、场景、范围、约束和验收口径，代理容易过早实现、静默猜测或遗漏失败路径，直到后期才暴露理解偏差。
- 期望结果：用户只需表达核心意图，插件便能从仓库事实与合理推断形成可审查契约；仅对高影响决策追问，其余可逆细节记录假设后推进，并以逐项证据完成验收。

## 已确认事实

- 插件必须同时服务 Claude Code 与 Codex。
- 插件面向提示词稀疏的氛围编程场景。
- 核心价值是减少返工，而非单纯生成更多文字。
- Skill 需要按产品研发角色明确分工。
- 工作流需要覆盖从需求形成到交付验收的完整生命周期。

## 推断需求

- “联想”必须受仓库事实、用户原话和现有约束约束，并明确标注为事实、推断或开放问题。
- 可从仓库查明的信息应自行查明，不应反问用户。
- 可逆且符合现有惯例的细节可作为假设继续；会显著改变产品方向、安全边界、外部状态或不可逆数据的选择必须取得确认。
- 端到端任务由编排角色推进；单一前端、后端、架构或验收任务仍可直接进入对应角色，但不得绕过其所需的上游契约。
- 生命周期闭环必须包含失败、恢复、回归与剩余风险，而非止于代码完成。

## 核心旅程

1. 用户输入一句简短意图，例如“做个团队知识库”或“给订单加批量退款”。
2. 编排角色读取仓库指令、现有行为、技术栈、已有改动与可复用约定，识别任务类型和影响边界。
3. 产品角色保留原始意图，补全目标用户、待完成任务、核心旅程、范围、状态、约束与验收标准，并为每项内容标注证据等级。
4. 只有高影响且无法从仓库得出的决策进入确认门；其余假设写入产品简报后继续。
5. 编排角色依据影响范围选择架构、前端、后端等专项角色，并为每一阶段声明输入、输出和完成门禁。
6. 专项角色在各自权限内实现并验证，不静默修改上游产品契约；新证据改变范围时退回对应上游阶段。
7. 验收角色把原始意图和验收标准逐项映射到实现证据，覆盖核心旅程、重要失败或恢复路径及回归检查。
8. 发布适用时，发布与运行角色在明确授权后执行部署门禁、迁移、回滚准备和上线后技术与业务验证。
9. 运行偏差与用户反馈回到产品角色，形成下一轮可验收增量；编排角色记录未通过项、既有失败与剩余风险。

## 范围

### 本次包含

- 强化短提示词的证据化扩写、假设分级与最少追问规则。
- 为七个生命周期 Skill 定义角色、输入、职责、输出、边界与交接门禁。
- 建立从产品简报、功能规格、架构决策、API 契约到验收报告的可追溯闭环。
- 更新共享模板、双端插件描述与 Codex Skill UI 元数据。
- 增强静态校验，确保角色集合、契约章节、模板和双端清单保持一致。

### 本次不包含

- 不增加 MCP、Hook、常驻服务、图形界面或外部模型调用。
- 不引入新的运行时依赖。
- 不自动安装或更新 Codex、Claude Code 中已经缓存的插件；发布角色作为共享能力实现，但本次源码改造不执行实际发布。
- 不建立没有执行器的评测样例目录。
- 不强制每个小改动生成全部文档；只生成当前路径所需的最小契约。

## 工作流状态

- 接入：已收到原始意图，尚未形成可实施契约。
- 待确认：存在会显著改变范围或风险的开放决策，暂停相关实现。
- 可实施：目标、边界、假设和验收标准已经足以支持当前切片。
- 实施中：专项角色按已确认契约推进。
- 验证失败：证据与验收标准不符，退回责任阶段修正。
- 已验收：所有实现标准均有当前证据，剩余风险已显式记录。
- 待发布：发布适用但尚未授权，或发布门禁尚未满足。
- 已发布：技术健康与核心业务成功信号均有上线后证据。
- 已回流：运行偏差或用户反馈已转成下一轮产品输入。
- 恢复：从持久化产物读取决策和未完成项，不依赖对话历史猜测上下文。

## 约束与假设

- 保留现有六个 Skill，不为“提示词扩写”另造脱离产品职责的新角色；新增 `release-operations` 承担原有角色未覆盖的发布、运行验证与反馈回流。
- `product-delivery` 是流程编排者，不代替专项角色做产品、架构、前端、后端或验收决策。
- `product-discovery` 对需求扩写与产品边界拥有唯一主责。
- `skills/` 与 `templates/` 是双端共享内核，平台 manifest 和 `agents/openai.yaml` 属于适配层。
- 用户已要求先编写插件源码，本次不执行安装和缓存版本更新。

## 验收标准

- [x] 短提示词任务会先读取仓库证据并形成包含原始意图、事实、推断、开放问题、范围和验收标准的产品契约。
- [x] 工作流能区分必须确认、可记录后继续和应自行查明三类信息，不以大量追问阻断氛围编程。
- [x] 七个 Skill 均明确角色定位、输入契约、职责、专业核心能力、输出契约、交接门禁与禁止越界事项。
- [x] 前端角色的专业能力明确覆盖易用性、交互简化、信息架构、响应式布局、色彩与排版协调、可访问性、状态工程和真实视觉验收。
- [x] 端到端、纯产品、纯前端、纯后端、架构、独立验收与发布任务均有明确路由，不强制经过无关阶段。
- [x] 下游发现范围变化、架构不变量或契约偏差时，能退回正确上游角色，而非静默改写决策。
- [x] 验收报告可将每条验收标准映射到当前证据，并区分本次回归、既有失败与剩余风险。
- [x] 发布适用时，工作流覆盖明确授权、制品追溯、迁移、技术与业务健康、停止条件、回滚及反馈回流。
- [x] Claude Code 与 Codex 共享同一组 Skill 和模板，两个 manifest 的共享元数据保持一致并分别通过校验。
- [x] 项目静态校验能发现缺失角色、缺失契约章节、断裂模板引用和双端 manifest 漂移。

## 开放问题

- 插件安装后的真实对话效果与返工率，需要在后续独立前向测试中度量；本次先建立可执行、可静态验证的行为契约。
