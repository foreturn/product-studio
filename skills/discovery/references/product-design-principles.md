# 产品发现能力手册

按当前产品问题从能力目录加载必要能力卡。每张能力卡给出触发条件、所需输入、执行方法、专业裁决、产物、证据、完成条件与职责边界；需要形成完整产品简报或处理变更时，再执行能力组合并核对完成判据。

## 能力目录

- [问题定义](#问题定义)：把功能形态还原为有证据、可观察的用户问题。
- [用户与任务建模](#用户与任务建模)：区分参与者的目标、情境、权限与失败代价。
- [证据化联想](#证据化联想)：从当前项目和外部材料形成可追溯、可证伪的产品判断。
- [旅程与状态设计](#旅程与状态设计)：建立从触发到结果、覆盖必要异常与恢复的完整旅程。
- [范围与优先级](#范围与优先级)：以价值、风险、依赖和学习裁出最小完整增量。
- [成功衡量](#成功衡量)：定义可归因指标、质量护栏和可判定验收标准。
- [澄清沟通](#澄清沟通)：自行查明事实，只上提会实质改变产品结果的决定。
- [能力组合](#能力组合)：按证据到验收的顺序组合多项能力。
- [完成判据](#完成判据)：判断发现结果能否无歧义交给设计、实现与验收。

## 核心能力

### 问题定义

- **启用**：
  - 原始提示简短，或直接指定按钮、页面、接口等功能形态。
  - 目标用户、触发场景、当前路径、具体阻碍、期望结果与改变价值任一项尚不明确。
  - 当前仓库事实否定原始问题假设，需要重新界定问题。
- **输入**：
  - 原始请求原文或忠实摘要，以及用户明确给出的目标、约束和非目标。
  - 当前产品行为、业务术语、相邻能力和已有替代方式。
  - 能够说明发生频率、紧迫性、持续时长和失败代价的证据；缺失项标为未知，不凭常识补齐。
- **执行**：
  - 依次回答：谁在何种情境触发、目前怎样完成、在哪一步因何受阻、使用何种替代方式、失败造成什么后果、理想结果是什么、为何值得现在改变。
  - 把方案表述改写为待验证的任务假设，不把实现形态直接写进问题陈述。
  - 对同一方案的不同任务目的分别推演。例如“增加导出按钮”可能服务跨系统交付、审计留档或离线分析；分别分析数据范围、格式、权限、时效与成功条件。
  - 描述当前状态与目标状态之间可观察、可验证的差距。
  - 分开记录原始意图、解释后的问题及两者映射，避免扩写过程覆盖原意。
  - 识别频率、紧迫性、持续时长、替代方案与失败代价，作为流程深度、默认行为和优先级的依据。
- **裁决**：
  - 当前证据支持的用户任务与可观察结果优先于功能形态、排期便利和既有假设。
  - 多个用户群体结果冲突时，分别列出受益、成本和风险，不用笼统“用户”合并利益差异。
  - 高频、低风险任务倾向缩短步骤；低频、高风险或不可逆任务倾向增加确认、解释和恢复。
  - 仓库事实否定问题假设时，保留原始意图并修订问题定义，不为预设方案寻找佐证。
- **产出**：
  - 原始意图及显式约束。
  - 包含主要用户、触发、现状、阻碍、替代方式、频率、失败代价、目标结果和改变价值的问题陈述。
  - 当前—目标差距、关键假设、证据引用及不得改变的现状。
  - 对多个实质解释保留带影响说明的分支，不伪装成单一结论。
- **验证**：
  - 以当前请求、已确认决定及现状行为与用户任务的对应分析作为直接证据。
  - 要求下游仅凭问题定义即可说明为何改变、要改变何种用户结果、哪些既有行为不得改变。
  - 功能名称、技术任务标题、扩写后的功能清单不足以单独证明问题成立。
  - “体验不好”“功能不完善”等无法观察的判断必须改写，不能作为完成证据。
- **完成**：
  - 目标用户、触发、现状、阻碍、替代方式、频率、失败代价、目标结果和价值均已明确或显式标记未知。
  - 当前与目标差距能够被观察或验证。
  - 原始方案只作为候选解法；更换实现形态后，问题定义仍然成立。
- **边界**：
  - 只裁决产品问题与目标结果，不决定组件、接口、数据模型或技术实现。
  - 不把用户所述方案直接当作问题，不因仓库已有代码就推定其符合需求，也不以功能清单变长代替问题清晰度。

### 用户与任务建模

- **启用**：
  - 流程包含主要使用者、审批者、数据所有者、运营者、被通知者或其他被影响者。
  - 参与者在目标、权限、专业程度、设备环境、任务频率或失败后果上存在差异。
  - “用户”一词掩盖了利益冲突或责任交接。
- **输入**：
  - 当前业务角色、权限配置与数据归属证据。
  - 核心任务的实际执行过程、触发情境和使用环境或设备。
  - 各类参与者的专业程度、任务频率与失败后果。
  - 画像缺少直接证据时，保留来源、置信度和待验证项，不套用通用 persona。
- **执行**：
  - 先找出直接完成核心任务并取得结果的主要用户。
  - 分别建模审批者、数据所有者、运营者、被通知者和被影响者，不因参与同一流程便赋予相同需求。
  - 为每类角色记录目标、触发、业务动作、环境或设备、专业程度、权限边界、数据关系、任务频率和失败后果。
  - 使用用户动作与业务目的命名任务，例如“确认结算结果”；不用表名、服务名或组件名充当产品概念。
  - 将旅程中每个动作绑定执行者，标出角色交接、权限冲突和利益冲突。
  - 对缺证据的画像说明验证它会改变哪些旅程、范围或验收项。
- **裁决**：
  - 角色是否纳入本轮，以其是否直接影响核心结果、必要授权、必要数据或高影响失败为准。
  - 高频、低风险用户优先减少步骤和选择；低频、高风险或不可逆任务优先增加确认、解释与恢复。
  - 专家与首次使用者需求冲突时，优先用合理默认、渐进披露或次级入口调和。
  - 无法调和的冲突分别记录受益、成本和风险，不静默牺牲任一群体。
  - 与核心结果无直接关系的角色进入非目标或后续研究。
- **产出**：
  - 用户—任务—触发—环境—权限—数据—频率—失败后果关系表。
  - 主要用户、其他参与关系和每步责任映射。
  - 角色冲突、取舍及带置信度的画像假设。
  - 画像验证结果可能影响的旅程、范围和验收项。
- **验证**：
  - 以当前业务角色、权限配置、现有界面和实际任务作为直接证据。
  - 对旅程每一步核对谁能做、为何做、对什么数据做、失败由谁承担。
  - 只有笼统“用户”或无来源的通用画像，不足以证明用户模型成立。
  - 把所有参与者视为共享相同目标和权限，视为建模失败。
- **完成**：
  - 核心旅程每个动作都有明确执行者和权限依据。
  - 主要用户与审批、运营、所有权、通知等关系没有混写。
  - 角色冲突已有调和方案或显式取舍。
  - 缺证据画像仍保持假设状态，并能说明验证影响。
- **边界**：
  - 只定义用户、任务、情境与产品层权限预期，不设计认证授权实现。
  - 不用组织职位自动替代真实任务角色，不为角色完整性引入无关范围。

### 证据化联想

- **启用**：
  - 需要从项目现状发现隐含需求、比较方案或校验假设。
  - 用户提供链接、截图、调研、竞品或其他项目材料，要求分析、比较或仿照。
  - 多个来源对同一行为给出不同结论。
- **输入**：
  - 可定位的实际界面、代码、配置、测试、日志、文档、相邻功能或数据生命周期材料。
  - 用户显式给出的外部来源及其身份、位置或链接。
  - 每份材料的观察时间、适用修订、可见范围与访问限制。
  - 无法访问或仅局部可见时，先记录证据缺口。
- **执行**：
  - 将每项关键结论标为用户已确认、当前仓库事实、外部参考、合理推断、约束或开放问题之一。
  - 仓库事实记录精确位置、观察到的行为和适用代码修订。
  - 外部材料记录来源、提取特征、借鉴目的及其对当前项目的适用性。
  - 推断记录依据、置信度、可逆性和验证方法。
  - 从相邻功能、导航、权限、错误行为、数据生命周期与测试中联想隐含需求。
  - 每项联想必须说明它服务哪个核心旅程、边界完整性或验收项。
  - 证据与问题、旅程、范围或验收条目建立双向关联。
- **裁决**：
  - 来源冲突时，优先核验与当前行为更直接、观察更新且对该事项更权威的来源。
  - 保留冲突、适用范围和取舍，不静默拼接成第三种事实。
  - 低置信且高影响的推断保持开放；低影响且可逆的推断可带失效条件推进。
  - 外部参考只有在当前目标和本项目证据支撑后，才能转化为产品决定。
  - 界面相似、竞品采用或其他项目成功，均不能自动证明当前用户偏好或本项目行为。
- **产出**：
  - 结论及来源类别。
  - 精确来源、观察时间或适用修订、提取特征和用途。
  - 适用范围、置信度、可逆性和验证方法。
  - 来源冲突、证据缺口及产品条目映射。
- **验证**：
  - 抽取任一关键结论，应能回到原始位置并复现所见事实。
  - 外部材料只能证明可见部分，不能证明本项目已有相同行为或当前用户接受对应偏好。
  - 未标来源的产品判断视为未经证明。
  - 只描述现有代码而不分析目标差距，不能证明现状符合需求。
  - 将外部字段、文案和规则全盘移植，不能证明其适用于当前项目。
- **完成**：
  - 所有会改变核心问题、旅程、范围或验收的结论均可追溯。
  - 事实、参考、推断和未知使用与证据强度相称的确定语气。
  - 冲突没有被掩盖；无法访问和局部可见材料的缺口与可借鉴范围已经明确。
- **边界**：
  - 只保留服务核心旅程、边界或验收的联想，不以联想数量衡量完整性。
  - 不补写未观察到的页面细节、商业逻辑或用户偏好，不用外部结果证明本项目已实现或安全。

### 旅程与状态设计

- **启用**：
  - 增量包含用户可见行为或业务状态变化。
  - 流程存在多入口、权限差异、异步等待、破坏性动作、失败、取消、中断或恢复。
- **输入**：
  - 已确认的问题定义和用户—任务—权限模型。
  - 当前入口、现有行为、目标结果和业务规则。
  - 已知风险、现有失败反馈及尚不稳定的前提。
  - 界面草图只能作为材料，不能替代旅程语义。
- **执行**：
  - 按触发、入口、必要输入、关键动作、系统反馈、最终结果写出最短快乐路径。
  - 说明每一步帮助哪类用户完成何种目标。
  - 逐步检查前置条件、权限、加载、首次使用、空白、部分数据、重复操作、取消、返回、失败、恢复和会话中断。
  - 为每个状态使用用户可理解的业务名称，并定义进入条件、可执行动作、系统反馈和离开条件。
  - 将失败区分为可重试、需修正输入、需等待外部条件和不可恢复，为每类失败匹配不同恢复动作。
  - 破坏性或不可逆动作执行前呈现对象、范围与后果，执行后呈现当前状态及可用恢复方式。
  - 多入口共享同一任务时统一核心规则与结果，只允许入口上下文影响默认值。
- **裁决**：
  - 快乐路径只证明理想条件可完成；高概率或高代价异常没有安全处置时，旅程仍不完整。
  - 异常状态按发生概率和失败代价决定覆盖深度，不机械枚举与任务无关的状态。
  - 旅程过长时，删除不服务结果的步骤、合并低价值选择或提供合理默认。
  - 不得通过隐藏风险信息、删除必要确认或省略恢复来缩短流程。
  - 多入口不得产生隐含的第二套业务语义。
- **产出**：
  - 从触发到结果的逐步用户旅程。
  - 状态—进入条件—可执行动作—系统反馈—离开条件矩阵。
  - 失败类别、恢复方式与责任角色映射。
  - 多入口一致性、破坏性确认、取消/退出与会话恢复规则。
- **验证**：
  - 从真实入口逐步走查到可观察结果。
  - 对适用的权限拒绝、空数据、部分数据、重复操作、取消、返回、外部等待、失败和恢复逐一给出可复现场景。
  - 页面列表、静态线框或只有成功动作的快乐路径不足以证明旅程完整。
  - 所有失败统一使用“稍后重试”，不足以证明恢复与失败原因匹配。
- **完成**：
  - 目标用户可从入口取得最终结果，每一步目的与反馈明确。
  - 高概率或高代价异常有对应状态和恢复。
  - 不可逆动作前后信息充分，多入口语义一致。
  - 会话中断后能够判断当前状态和下一可用动作。
- **边界**：
  - 只定义用户可观察行为、业务状态和产品恢复语义，不裁决组件、接口、存储或队列方案。
  - 不把快乐路径当完整旅程，不以隐藏风险或忽略恢复换取步骤更少。

### 范围与优先级

- **启用**：
  - 候选需求较多、MVP 边界不清或多个能力竞争资源。
  - 范围超出当前可验证能力、出现静默膨胀，或新增功能可能收缩既有行为。
- **输入**：
  - 核心用户结果、完整旅程及候选能力。
  - 每项候选的风险、依赖、学习价值和验证成本。
  - 当前交付能力及不得破坏的既有行为。
  - 每个候选项必须说明它改变哪个用户结果或状态。
- **执行**：
  - 将候选项分为核心价值不可缺少、提升闭环完整性、可独立延后、明确不做四类。
  - 为每项分类写出它与核心旅程的关系。
  - 按用户价值、风险降低、依赖顺序、学习价值和验证成本排序。
  - 仅在其他条件相当时，将实现容易作为次级排序因素。
  - 新增范围逐项说明改变的用户结果、影响状态、新增风险和新增验收。
  - 非目标同时说明本轮不做什么，以及哪些既有行为必须保持不变。
  - 范围超出验证能力时，切出能够产生真实学习的最小增量。
- **裁决**：
  - MVP 是最小而完整的端到端价值闭环，不是各技术层各做一部分。
  - 缺少必要失败恢复或结果反馈的快乐路径通常不完整。
  - 能力竞争时，优先保留对核心结果不可替代且能降低重大不确定性的部分。
  - 增强性细节在核心闭环后独立推进。
  - 新证据使原排序失效时，重算受影响项并记录原因，不为维护旧排期继续低价值工作。
- **产出**：
  - 带分类理由、旅程关联和优先依据的范围表。
  - 每项范围的依赖、风险、验证方式和验收映射。
  - 明确非目标、不得破坏能力、后续研究和范围变化记录。
- **验证**：
  - 逐项询问：删除它是否仍能取得核心结果、延后它会增加何种风险、怎样独立验证。
  - 范围内每项均须映射用户结果和验收，分类理由须由当前证据支撑。
  - 无优先依据的功能池或按实现容易排序，不能证明优先级合理。
  - 各技术层半成品或无依据增强项堆叠，不能证明 MVP 完整。
- **完成**：
  - 核心闭环在当前范围内可交付、可验收，必要失败与结果反馈已经覆盖。
  - 增强与后续能够独立延后。
  - 非目标及既有不变行为足以让下游识别误删和行为收缩。
  - 所有新增范围都有显式影响、风险与验收。
- **边界**：
  - 只裁决产品价值范围与优先级，不决定技术拆分和具体排程。
  - 不把实现容易等同优先级高，不以宏大目标掩盖不可判定状态，不静默吸收新范围。

### 成功衡量

- **启用**：
  - 需要判定增量是否创造用户或业务价值、是否满足质量底线。
  - 需要为设计、实现和独立验收提供稳定、可判定的产品标准。
- **输入**：
  - 目标用户、核心旅程、业务结果和适用风险。
  - 当前可观察数据、已有基线及证据采集能力。
  - 无法采集或没有基线的事项必须显式列出，不虚构数据来源与阈值。
- **执行**：
  - 同时选择用户结果、业务结果与质量护栏。
  - 可选信号包括任务完成率、完成耗时、错误率、数据正确性、人工介入次数和恢复成功率。
  - 每项指标写明观察对象、计算口径、时间窗口、基线或目标、数据来源和异常解释。
  - 缺少数据时定义可采集的代理信号或建立基线计划。
  - 以稳定 `AC-ID` 编写“给定前置条件—执行动作—可观察结果”的验收标准。
  - 每条标准只判断一个结果，并补充适用的权限、失败和恢复行为。
- **裁决**：
  - 指标只覆盖当前增量能够合理影响且能够观察的结果。
  - 不用无法归因的总收入、总活跃等宏大数字衡量局部改动。
  - 数值阈值没有依据时，标为待建基线或显式假设，不凭行业想象造数。
  - 产品验收保持实现中立；用户结果不变时，实现方式变化不应使标准失效。
  - 覆盖深度由核心旅程与高影响边界决定，不把所有内部细节写入产品标准。
- **产出**：
  - 指标清单及每项口径、窗口、基线或目标、来源与异常解释。
  - 缺数据事项的基线计划或代理信号。
  - 质量护栏。
  - 带稳定 ID、适用状态和证据映射位置的验收标准集。
- **验证**：
  - 每项指标能够说明数据从何处取得、怎样计算、何时观察及异常如何解释。
  - 每条验收可独立标记通过、失败、阻塞或不适用，并链接直接证据。
  - “体验良好”“性能足够”“支持完整”“提升活跃”等愿望句不能作为验收。
  - 没有口径、来源或归因关系的数据不能证明成功。
- **完成**：
  - 核心结果和适用的权限、失败、恢复均有单一可判定验收。
  - 成功信号可归因、可观察，且有口径、窗口和来源。
  - 无依据阈值与不可采集项已转为显式假设、基线计划或代理信号。
- **边界**：
  - 只定义产品结果与质量护栏，不指定测试工具或实现细节。
  - 不把愿望句当验收，不以宏大指标代替本增量效果，不为覆盖数量写入无关实现细节。

### 澄清沟通

- **启用**：
  - 未知答案可能改变目标用户、核心结果、旅程、MVP 或高影响边界。
  - 未知涉及权限安全、付费外部状态、不可逆数据、精确值、凭据或授权。
  - 普通事实调查和局部可逆细节不因本能力启用而停止。
- **输入**：
  - 已核验事实、当前假设和未知项。
  - 可选方案、各自影响范围与可逆性。
  - 哪些旅程或切片真实依赖答案。
  - 将精确值、凭据、授权类缺口与产品偏好类决定分开。
- **执行**：
  - 将未知分为可自行查明、可按显式假设推进、必须由有权者裁决三类。
  - 阅读项目、材料并使用安全只读检查查明第一类。
  - 为第二类记录依据、置信度、失效条件与恢复点后继续工作。
  - 将第三类压缩为最小决定集。
  - 对可选择的问题给出两到三个真实选项，说明各自对用户结果或风险的影响，并给出基于证据的建议。
  - 所需内容只是精确值或授权时，直接请求该值或授权，不编造伪选项。
  - 只阻塞真实依赖答案的旅程或切片；无关调查、证据整理和稳定部分继续推进。
- **裁决**：
  - 只有会实质改变产品结果或高影响边界、且无法由现有事实确定的未知才上提。
  - 可逆、局部且符合当前惯例的细节以显式假设推进。
  - 新证据推翻假设时标记失效，沿依赖关系回到最近仍成立的产品事实。
  - 决定形成后同步更新问题、旅程、范围、指标和验收，不能只修改最终结论。
- **产出**：
  - 可查事实的核验结果。
  - 带依据、置信度、失效条件和恢复点的假设。
  - 少量高影响决策卡及选项—影响—建议。
  - 局部阻塞范围和决定形成后的变更清单。
- **验证**：
  - 所有可从仓库、现有材料或安全只读检查获得的事实均已查明。
  - 每个开放问题都能说明不同答案将改变何种产品结果或风险。
  - “请提供完整需求”“具体想怎么做”不能代替产品拆解。
  - 把代码调查交回提问，或为微小偏好阻塞整段工作，均不构成有效澄清。
- **完成**：
  - 可查事实已核验，可逆细节有明确假设与失效条件。
  - 高影响未知数量最小，并有可裁决选项或精确请求。
  - 阻塞只覆盖真实依赖项。
  - 已形成决定已经同步到所有受影响产品结论。
- **边界**：
  - 不替有权者确认高影响选择、授权、凭据或不可逆后果，也不把所有未知都上提。
  - 产品拆解必须先于提问；无法提供真实选项时，明确说明缺少的是何种事实或授权。

## 能力组合

1. **保留原意**：记录原始请求及显式目标、约束与非目标；任何解释后的方案都不得冒充原始意图。
2. **核验现状**：检查当前产品行为、业务术语、相邻能力、权限、错误行为、数据生命周期和显式外部参考，分列用户确认、事实、参考、推断、约束与未知。
3. **定义问题**：明确主要用户、触发场景、当前路径、具体阻碍、替代方式、发生频率、失败代价、期望结果和改变价值，不把提议方案当唯一答案。
4. **建立用户模型与旅程**：区分主要用户及其他关系，先形成从触发到结果的最短动作链，再补当前任务适用的权限、空白、部分数据、重复、取消、返回、失败、恢复和退出状态。
5. **识别高险未知**：判断未知会否改变用户、核心结果、范围、权限、付费外部状态或不可逆边界；继续查明事实，以带失效条件假设推进局部可逆细节，只保留少量高影响决定。
6. **裁剪范围**：按核心不可缺少、提升完整性、可延后与明确不做分类，以价值、风险、依赖、学习和验证成本排序，并保护不得收缩的既有行为。
7. **定义成功**：选择当前增量可归因、可观察的用户结果、业务信号与质量护栏；缺少基线时定义取数计划或代理信号。
8. **编写验收**：把每个核心结果及适用的权限、失败和恢复写成带稳定 ID 的单一可判定标准，使下游直接理解要实现什么、不得改变什么。
9. **一致性复核**：逐项核对问题、用户、旅程、范围、指标与验收是否相互支撑；删除没有用户结果依据的功能，补齐没有验收覆盖的核心行为。
10. **变更收口**：新证据出现时标记失效假设、被取代结论、受影响范围与下游消费者，从最近仍成立的产品事实继续演进。

相邻步骤结论冲突时，回到来源更直接、更新且与当前用户结果更接近的证据；产品问题与可观察结果优先于功能形态、排期便利和旧假设，同时保留取代关系与受影响范围。

## 完成判据

- 原始意图、问题定义、用户模型、证据索引、旅程、范围、指标、验收、开放决定和变更影响均有明确消费者；不为形式完整生成当前任务不需要的产物。
- 问题定义包含用户、触发、现状、阻碍、替代方式、频率、失败代价、结果与价值，当前—目标差距可观察；功能名称或技术任务标题未被当作问题本身。
- 用户模型区分主要用户、审批者、数据所有者、运营者、被通知者与被影响者，且目标、权限和失败代价没有混写；无来源画像仍保持假设状态。
- 关键结论均标明来源类别、精确依据、适用修订或观察时间、置信度与验证方法；外部材料只支持其可见部分，未被当作当前项目事实或用户偏好。
- 核心旅程从入口到结果闭合，适用的权限、空白、部分数据、重复、取消、返回、失败、恢复和中断有明确状态；快乐路径、页面列表或统一“稍后重试”未被当作完整旅程。
- MVP 是可取得真实结果的端到端闭环，范围内每项映射用户结果与验收；实现容易、功能数量或技术分层未被用作主要优先依据；非目标和不得破坏的既有行为足以识别行为收缩。
- 指标具有对象、口径、窗口、基线或目标、来源和异常解释；没有依据的阈值仍为假设或基线计划；每条验收均为单一、可观察、可判定结果，并能映射直接证据。
- 可查事实已经自行核验，可逆细节以带失效条件的假设推进；只有会改变产品结果或高影响边界的未知被上提，且阻塞没有扩散到无关工作。
- 新证据引起的取代关系及其对问题、旅程、范围、指标、验收和下游消费者的影响已经同步，不存在只改最终方案而上游互相矛盾的情况。
- 若仍出现以下任一情形，则不得宣告产品发现完成：把用户方案当问题、把所有参与者当同一用户、把仓库存在当需求符合、把外部页面直接变成需求、以联想数量代替证据、只写快乐路径、把 MVP 切成各层半成品、按实现容易排序、使用不可归因宏大指标、用愿望句写验收、把所有未知交回提问，或发现新证据后只改结论。
