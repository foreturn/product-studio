# 安全工程 · 威胁建模与对抗验证

### 资产、数据流与威胁建模

- 威胁模型必须从受保护资产、攻击者能力、实际数据流和信任跨越推导，不能套用与系统无关的通用清单。
- 每条高风险路径都应说明攻击前提、影响范围以及预防、限制、检测与恢复机制。
- 控制必须映射到不可绕过的代码、配置或运行边界；文档中存在控制名称不能证明控制实际生效。
- 内部网络、受管设备、同一运行环境和已认证主体都不自动可信，仍需按最小信任验证动作与资源。
- 管理面、后台任务、消息处理、内容解析和第三方回调必须纳入与用户入口同等的攻击面分析。
- 未验证假设和剩余风险必须与已缓解事实分开，入口、身份、数据或部署边界变化时重新审视相关威胁。
- 新控制应优先接入既有身份、策略、秘密、审计和响应体系；局部自建的平行安全机制若无法共同撤销、观测和演进，便会形成新的绕过面。
- 控制实现应区分政策数据、可信上下文、决策与强制执行责任，使允许、拒绝和失效行为可审查；控制复用须保留各入口的信任条件、策略语义与强制执行点，不能为代码去重合并不同信任边界或删除独立防护。

### 漏洞确认与对抗验证

- 漏洞确认必须在明确授权的资产和影响范围内进行，以最小副作用证明攻击前提、可达性、影响和不可利用对照。
- 根因应定位到实际控制点，并沿同类数据流、角色、租户和入口寻找变体，不能只修复单个样本。
- 风险等级必须综合影响、暴露、利用难度、现有控制、检测和恢复，扫描结果与通用评分只能作为线索。
- 临时缓解必须说明覆盖范围、可观测性和失效条件，外围拦截、隐藏入口和文档警告不能代替根因修复。
- 对抗验证应按风险选择属性测试、解析鲁棒性、授权矩阵和端到端攻击路径，并限制测试资源与环境副作用。
- 修复结论需要原路径、绕过变体和正常业务回归共同证明，无法稳定复现或只有单一扫描结果不能宣称已经修复。
