# 交付验证能力准则

## 要求追溯与风险建模

- 从原始意图、产品范围、架构决定、契约和迁移约束导出完整要求，不从实现反向定义成功。
- 为每项要求记录实现位置、验证方法、环境、证据和通过、失败或阻塞结论。
- 按用户影响、发生可能性、可发现性、数据不可逆性、安全边界和改动复杂度确定验证优先级。
- 优先验证高影响、高不确定和历史易错区域，再覆盖低风险细节。
- 检查完整差异与调用链，识别间接消费者、共享组件、配置、数据和发布影响。
- 回归范围从完整代码差异出发，沿调用链上下游追踪直接消费者、间接消费者与跨模块受影响的旧能力；不只验证本次新增的快乐路径，还要证明旧能力未被破坏，避免只盯改动点而遗漏既有调用方。
- 风险分级决定验证深度与顺序：触及数据持久化、权限安全、外部集成或兼容契约的改动深验，纯展示文案、内部工具等低风险改动可从简，但不得跳过回归确认。

## 分层测试策略

- 静态检查证明语法、类型和规则；单元测试证明局部逻辑；契约测试证明边界；集成与端到端证明协作与旅程。
- 选择最小但充分的组合，不用大量重复单元测试制造虚假信心，也不用一个端到端测试包揽全部定位责任。
- 核心业务规则优先使用确定性测试；时间、随机、网络和外部依赖要可控制或可替代。
- 每个关键快乐路径至少配一个重要边界、失败或恢复路径。
- 测试数据覆盖空值、边界值、重复、乱序、过期、权限差异、旧版本和部分成功。
- 按风险把每项要求落到最合适的层：权限、并发、迁移、外部集成等高风险能力确认有对应层覆盖；不在多层级重复同一断言制造冗余信心，也不让某层独自承担其不擅长的责任（如单元测试不背权限，端到端测试不负责精确定位）。

## 前端与体验验收

- 走完核心任务并计算不必要步骤、重复输入、迷失点和无法恢复的错误。
- 检查信息层级、主次动作、内容密度、对齐、间距、长文本、动态内容和桌面移动端布局。
- 检查品牌色、状态色、中性色、背景和文字对比是否协调，信息是否只靠颜色表达。
- 覆盖加载、空白、错误、成功、权限不足、禁用、提交中和恢复状态，检查反馈及时且文案可行动。
- 用键盘完成核心流程，检查焦点、标签、辅助名称、触控尺寸、减少动画和辅助技术通知。
- 查看实际浏览器控制台、网络和资源；截图或视觉检查必须对应代表性视口与状态。

## 后端、数据与集成验收

- 校验 API 请求响应、错误语义、权限、数据范围、分页筛选和兼容行为。
- 检查事务、幂等、并发、重复请求、重试、部分失败和最终状态，不只验证单线程快乐路径。
- 验证数据库约束、索引影响、迁移前后数据、回滚和新旧代码共存。
- 模拟依赖超时、错误、限流和不可用，确认降级、隔离、补偿与可观察结果。
- 检查日志是否可关联且不泄密，指标和健康检查是否真正反映业务结果。

## 非功能与发布就绪

- 性能验证围绕明确负载、数据量、延迟或资源目标；没有基线时只报告测量结果，不虚称达标。
- 安全验证围绕当前信任边界检查认证、授权、输入、敏感数据、审计和高价值操作。
- 可靠性验证覆盖重启、超时、重试、积压、容量与恢复；按风险决定是否需要压力或长稳测试。
- 检查构建制品、配置、迁移、回滚、监控和运行说明是否足以进入发布阶段。
- 安全验收必查项：水平与垂直越权（列表与详情使用一致权限并分别验证）、SQL 与命令注入、敏感字段在日志/响应/异常中的泄露、批量枚举与资源耗尽、以及与入口相关的重放与反序列化风险。

## 证据与结论纪律

- 只有确认命令、测试、截图或日志实际覆盖某项要求后，才能将其作为该项证据。
- 记录命令、关键输入、环境、时间、结果和证据位置，使他人能够复现。
- 首个可行动失败优先报告；区分本次回归、既有失败、环境阻塞、未验证和剩余风险。
- 一项必需标准缺少直接证据时，总体不得通过；“未发现错误”不等于“已证明正确”。
- 不为通过而降低标准，不顺手修复无关问题，也不把局部绿灯外推为端到端打通。
- 证据与要求的映射就位后才能采用其结论：不因同层或相邻测试通过而外推未实测的能力，也不以一个绿灯覆盖多个独立要求。
