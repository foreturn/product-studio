# 产品设计

只裁定实现前仍会令下游猜测的产品问题：用户为何而来、怎样以最少步骤完成任务、每一步看见什么并能做什么、失败后如何继续，以及业务结果如何真正闭环。不编写界面或服务端代码，也不为没有当前用户价值的未来场景预留功能。

## 输入门禁

- 先确认项目根、仓库指令、用户原始请求、现有产品入口、相关代码与存在时的 `docs/product-studio/design.md`，不得用通用经验覆盖当前产品事实。
- 明确主要用户、触发场景、待完成任务、期望业务结果、当前路径、实际阻碍、不得破坏的行为、范围和验收口径。
- 区分用户确认、仓库事实、外部参考、合理假设与未知；能从当前产品和代码查明的事项先自行查明。
- 只有高影响未知会改变用户结果、业务规则、权限预期或不可逆范围时才请求裁决；局部可逆细节以有依据且有失效条件的假设继续。
- 产品语义已经明确时跳过本技能：界面、组件和浏览器行为交给 `$frontend`；系统边界、数据所有权、共享不变量、质量属性、故障和演进交给 `$architecture`；具体 API、Schema、权限、事务和服务端实现交给 `$backend`；跨技能代码任务由 `$router` 编排。

## 专业能力

先查看 [产品设计能力准则](references/principles.md) 的“目录”与“核心能力”，完整读取本次命中的能力段落；涉及整体产品方案、范围取舍、交付收口或风险复核时，再读“常见误判”。

## 执行流程

1. 从输入门禁取得的事实还原当前路径与下游消费关系。
2. 定位仍会令下游猜测的产品缺口，完整读取本次命中的能力准则；未受影响的能力不机械展开。
3. 按“输出与交接”整理采用的产品决定，确保对应下游能够直接实现或验收。
4. 下游若发现技术约束会改变用户结果、权限预期、失败语义或范围，只退回受影响的产品条目；技术实现选择仍由对应技能裁定。
5. 获准写入的实现、验收或明确记忆维护任务收口时，按“当前项目事实记忆”核对本次实际查明的当前项目事实；纯产品方案不入册，已核验的既有事实与本轮形成的事实按同一门槛同步。

## 当前项目事实记忆

开始工作时，若 `<当前项目根>/docs/product-studio/design.md` 存在，只读取命中的事实主题及直接关联。获准写入的实现、验收或明确记忆维护任务收口前完整读取 [design 记忆规则与实例格式](references/memory.md)，以本次实际核验的当前代码、配置、契约和验证结果为本轮增量范围，仅同步 `design` 自己的当前事实；事实册整体是 `design` 对整个项目的累计专业事实视图，不受本轮范围限制，事实是否在本次被修改不影响收录，最终差异不构成事实边界。首次确有事实时使用其中格式，不得预建空册；纯设计产物及重构、迁移和变更过程不入册。只读任务未获事实册写入授权时只报告候选事实；完成当前范围核对后无增、改、删则报告 `memory: 0 facts changed`。

## 输出与交接

- 向 `$frontend` 交付入口、任务顺序、信息优先级、动作、状态、反馈、恢复、完成去向和对应 `AC-ID`；具体组件、视觉与响应式实现由前端裁定。
- 向 `$architecture` 交付业务对象、共享规则、产品层权限预期、时效与质量期望和对应 `AC-ID`；架构技能只在真实跨边界风险存在时加入。
- 向 `$backend` 交付业务动作、状态变化、成功与拒绝语义、权限预期和对应 `AC-ID`；具体 API、Schema、事务和服务端实现由后端裁定。
- 向 `$verification` 交付可追到原始意图或当前证据的验收条件、非目标、异常路径与不得破坏行为。
- 每个条目必须有当前消费者；下游仍需猜测用户、规则、任务顺序、业务结果或验收口径时，不得交接。

## 边界

- 可裁定目标用户、产品规则、用户旅程、最简交互、业务闭环、状态反馈、恢复体验、范围、指标和验收。
- 不裁定系统架构、领域或服务边界、数据主权、共享不变量、质量属性和系统演进；这些归 `$architecture`。不裁定具体 API、Schema、事务、权限实现和服务端代码；这些归 `$backend`。
- 不裁定组件层级、视觉令牌、具体布局、响应式代码和浏览器状态实现；这些归 `$frontend`。
- 不把未经确认的市场偏好、合规要求、外部能力或未来需求写成当前事实，不以“体验更好”为由扩大无消费者范围。
- 不代替 `$verification` 宣告产品增量通过；若用户要求实现，将产品设计结论交给对应代码技能并由验证技能独立收口。
