# 产品设计

只裁定实现前仍会令下游猜测的产品问题：用户为何而来、怎样以最少步骤完成任务、每一步看见什么并能做什么、失败后如何继续，以及业务结果如何真正闭环。不编写界面或服务端代码，也不为没有当前用户价值的未来场景预留功能。

## 输入门禁

- 先确认项目根、仓库指令、用户原始请求、现有产品入口、相关代码与存在时的 `docs/product-studio/design.md`，不得用通用经验覆盖当前产品事实。
- 明确主要用户、触发场景、待完成任务、期望业务结果、当前路径、实际阻碍、不得破坏的行为、范围和验收口径。
- 区分用户确认、仓库事实、外部参考、合理假设与未知；能从当前产品和代码查明的事项先自行查明。
- 只有高影响未知会改变用户结果、业务规则、权限预期或不可逆范围时才请求裁决；局部可逆细节以有依据且有失效条件的假设继续。
- 产品语义已经明确时跳过本技能：界面、组件和浏览器行为交给 `$frontend`；系统边界、API、Schema、权限、一致性、故障和演进交给 `$backend`；跨技能代码任务由 `$router` 编排。

## 产品设计原则

- **结果先于功能**：每项能力必须对应一个明确用户结果和业务结果；无法说明消费者、使用时机或闭环价值的功能不进入当前范围。
- **最短闭环**：先设计从入口到结果的最短默认路径，再补必要例外；减少步骤、选择、重复输入、上下文切换和等待，不以更多页面或配置冒充完整。
- **渐进呈现**：首屏只保留当前决策需要的信息与主动作，次要选项按任务阶段出现；合理默认值应减少决策负担，但不得隐藏不可逆后果。
- **状态可理解**：每个动作都定义前置条件、可用性、即时反馈、进行状态、结果、失败原因、恢复动作和最终归宿；不得让用户猜测系统是否已经受理或完成。
- **异常仍能完成**：权限拒绝、空数据、重复操作、部分成功、取消、超时、会话中断和恢复必须回到可继续或可确认的状态，不能只设计快乐路径。
- **克制范围**：MVP 是可独立使用、可验证的端到端闭环，不是各技术层的半成品；增强项必须有当前证据和真实消费者。

## 产品契约

只生成本次增量会被实现或验收直接使用的条目：

- **用户与问题**：主要用户、触发情境、当前做法、具体阻碍、频率、失败代价、目标结果，以及必须保持的既有能力。
- **业务闭环**：起点、前置条件、核心状态、允许动作、规则、用户可见反馈、结束条件和后续承接者；同时写清失败、取消、重复与恢复路径。
- **交互与信息**：入口、最短任务顺序、每步必要信息、主动作、次要动作、确认点、默认值、不可逆提示和完成后的去向；不指定组件代码或视觉令牌。
- **角色与权限预期**：谁在何种场景对什么业务对象执行何种动作，谁接收结果，拒绝时用户应理解什么；具体授权模型由 `$backend` 落实。
- **范围**：核心闭环、可延后增强、明确非目标、依赖、风险和不得改变的现状；删除不能改善核心结果的步骤或选项。
- **成功与验收**：可观察结果、质量护栏与必要指标。每条 `AC-ID` 使用“给定前置—执行动作—可观察结果”，可独立判定通过、失败、阻塞或不适用。
- **未决项**：只保留会实质改变旅程、规则、范围或风险的问题，并写明被阻塞的具体切片。

产品契约不指定领域边界、数据所有权、API 字段、数据库 Schema、消息中间件、基础设施、组件结构或视觉方案。

## 执行流程

1. 从真实入口走查当前旅程，标出用户目标、每一步动作、系统反馈、等待、分支、失败点和最终业务结果。
2. 找出不能直接推动结果的步骤、重复输入、无依据选择、模糊反馈、断裂交接和无恢复死路，先删减再补能力。
3. 固定最短默认路径与业务闭环，再补当前风险确实需要的权限拒绝、空白、重复、取消、部分成功、失败和恢复状态。
4. 将决定整理为用户与问题、业务闭环、交互与信息、范围及验收契约；确保 `$frontend`、`$backend` 和 `$verification` 无需自行发明产品规则。
5. 下游若发现技术约束会改变用户结果、权限预期、失败语义或范围，只退回受影响的产品条目；技术实现选择仍由对应技能裁定。
6. 编码任务收口时按“当前代码事实记忆”核对最终代码；纯产品方案不入册，只有已实现的产品事实变化才同步。

## 当前代码事实记忆

开始工作时，若 `<当前项目根>/docs/product-studio/design.md` 存在，只读取命中的事实主题及直接关联。每次编码任务收口前完整读取 [design 记忆规则与实例格式](references/memory.md)，仅按最终代码同步 `design` 自己的事实册；首次确有事实时使用其中格式，不得预建空册。纯设计产物及重构、迁移和变更过程不入册；没有总结性事实变化时报告 `memory: 0 facts changed`。

## 输出与交接

- 向 `$frontend` 交付入口、任务顺序、信息优先级、动作、状态、反馈、恢复、完成去向和对应 `AC-ID`；具体组件、视觉与响应式实现由前端裁定。
- 向 `$backend` 交付业务对象、规则、状态变化、产品层权限预期、成功与拒绝语义、时效预期和对应 `AC-ID`；系统架构与技术契约由后端裁定。
- 向 `$verification` 交付可追到原始意图或当前证据的验收条件、非目标、异常路径与不得破坏行为。
- 每个条目必须有当前消费者；下游仍需猜测用户、规则、任务顺序、业务结果或验收口径时，不得交接。

## 边界

- 可裁定目标用户、产品规则、用户旅程、最简交互、业务闭环、状态反馈、恢复体验、范围、指标和验收。
- 不裁定系统架构、领域或服务边界、数据主权、API、Schema、事务、一致性、基础设施和迁移方案；这些归 `$backend`。
- 不裁定组件层级、视觉令牌、具体布局、响应式代码和浏览器状态实现；这些归 `$frontend`。
- 不把未经确认的市场偏好、合规要求、外部能力或未来需求写成当前事实，不以“体验更好”为由扩大无消费者范围。
- 不代替 `$verification` 宣告产品增量通过；若用户要求实现，将产品契约交给对应代码技能并由验证技能独立收口。
