# 产品与系统设计

本技能只解决实现前仍会令 `frontend`、`backend` 或 `verification` 猜测的产品语义与系统约束。它不代替实现技能编码，也不因任务看似“完整”便机械生成产品文档或架构图。

## 启用判定

先检查当前仓库、已有决定和 `docs/product-studio/design.md`，再按实际缺口、影响半径、失败代价与可逆性选择最小模式：

- **只用产品模式**：目标用户、触发条件、业务规则、核心旅程、异常恢复、范围、非目标、成功口径或验收结果仍不明确，但技术边界没有发生跨域变化。
- **只用系统模式**：产品目标与验收已明确，但改动触及多个模块或进程、共享不变量、数据所有权、同步／异步协作、信任边界、质量属性、运行拓扑或新旧版本共存。
- **双模式**：短提示词既没有稳定产品契约，又会改变系统边界，且两者互相制约。先完成产品模式，固定用户结果、业务规则和验收；再把这些约束作为系统模式输入，不得并行推导两套相互矛盾的事实。若系统限制会改变用户结果、权限、失败语义或范围，返回产品模式只修订受影响条目。
- **跳过本技能**：局部页面、组件、样式、查询、接口实现或缺陷修复的行为契约与影响边界已经清楚。直接调用 `frontend` 或 `backend`，完成后交给 `verification`。

单纯需要安排技能顺序时交给 `router`；只有出现上述产品或系统缺口时才进入本技能。

## 条件加载专业能力

产品模式以本文件的产品契约为专业指引，系统模式按需加载独立架构准则，二者仍保持单一 `design` 技能内的模式隔离：

- 产品模式不加载独立 reference，直接依据本文件的启用判定、共同证据基线、产品模式下游契约与执行顺序。
- 系统模式先查看 `references/architecture-principles.md` 的“目录”与“核心能力”，完整读取本次命中的能力段落；需要形成完整系统契约时，再读取其“常见误判”。普通局部实现不能借“可扩展性”之名触发系统设计。
- 双模式先依本文件的产品模式固定用户结果、业务规则和验收，再把产品契约作为系统模式输入，依系统能力准则裁决边界与质量属性。系统方案不得反向虚构用户需求；技术限制若迫使用户结果、业务规则或范围改变，必须回到产品模式重新裁决受影响条目。

`references/architecture-principles.md` 只保存系统设计的能力、判断方法和证据标准。本文件负责产品模式、触发判定、模式顺序、下游契约与代码事实收口；目录摘要和本节概述均不能代替系统模式命中的专业正文。

设计契约中的 `AC-ID`、ADR、状态、候选取舍和取代关系属于本轮可审计设计契约，或属于当前项目已经采用且本次明确需要维护的正式产品／架构文档；它们不属于 `docs/product-studio/` 代码事实记忆。跨会话需要持久化这些设计产物时，沿用项目既有文档位置或先取得明确范围，不得借代码事实模板保存过程与历史。

## 共同证据基线

设计前必须取得与本次裁决有关的直接证据：

- 当前项目根、仓库指令、相关代码、Schema、配置、测试、界面和已有记忆事实。
- 用户原始请求、已确认目标、明确约束、非目标以及不得破坏的既有行为。
- 实际入口、调用方、消费者、业务对象、数据所有者、外部依赖、运行单元和诊断信号。
- 外部资料的精确来源、可见范围、版本或观察时间；外部案例只作为候选证据，不自动成为当前项目事实。

每项关键结论须区分用户确认、仓库事实、外部参考、合理假设、约束和未知。能从仓库与安全只读检查查明的事项先自行查明；只有不同答案会实质改变用户结果、高风险边界或不可逆后果时才请求裁决。

## 产品模式的下游契约

根据当前产品事实与本文件的产品模式约束，只生成当前增量确实需要的条目；每项条目都必须能被实现或验收直接采用：

- **问题契约**：主要用户、触发情境、当前路径、具体阻碍、替代方式、频率、失败代价、目标结果、改变价值及不得改变的现状。
- **用户与权限预期**：每个动作的执行者、业务目的、对象范围、产品层权限预期、数据关系、角色交接和失败承担者；不得用笼统“用户”掩盖差异。
- **业务规则与旅程**：前置条件、状态、允许动作、系统反馈、结束条件；覆盖当前任务适用的权限拒绝、加载、空白、部分数据、重复、取消、失败、恢复与会话中断。
- **范围契约**：核心闭环、增强项、可延后项、明确非目标、依赖、风险以及必须保持的既有行为；MVP 必须形成端到端可验收结果，不得切成各技术层半成品。
- **成功与验收契约**：可归因指标的对象、口径、窗口、基线或目标、数据来源和质量护栏；每条 `AC-ID` 使用给定前置—执行动作—可观察结果，单独可判定通过、失败、阻塞或不适用。
- **未决项**：仅保留高影响问题，写清不同答案改变的旅程、范围或风险以及被阻塞的具体切片；局部可逆细节以带依据和失效条件的假设继续。

产品模式不指定组件结构、API 字段、数据库 Schema、消息中间件或基础设施方案。

## 系统模式的下游契约

根据已加载能力卡，把跨边界决定写到实现者无需猜测的粒度：

- **上下文与所有权**：入口、模块、进程、存储、外部依赖、运行位置、信任边界、调用方、消费者、副作用和诊断信号；每项核心数据只有一个写入权威。
- **跨边界不变量**：可证伪规则、所有者、执行点、事务范围、违规表现、监测方式、修复动作及派生副本的陈旧度和重建路径。
- **同步与事件契约**：操作语义、请求响应、错误分类、超时、取消、幂等、权限上下文、版本兼容；事件生产条件、事实时间、顺序键、投递语义、重复、乱序、重放、死信和消费者责任。
- **质量属性场景**：刺激、环境、受影响组件、预期响应、量化阈值与现行基线；候选比较必须包含沿用现状或局部修补，并计入开发、迁移、基础设施、监控和维护复杂度。
- **故障与安全约束**：事务提交点、部分成功、重试唯一责任层、补偿与人工路径、恢复顺序；身份来源、租户与资源授权点、数据分类、滥用路径、审计及依赖故障时的拒绝或降级行为。
- **可观测与演进契约**：业务成功、拒绝、失败、延迟和积压信号，存活／就绪／业务可用语义；兼容扩展、双版本代码、迁移程序、读写路径选择、验证和旧路径清理的进入条件、可重入点与数据后果。
- **设计决定**：当前问题、已知约束、简单基线、候选、采纳方案、代价、可逆性、适用范围、验证办法和重审触发。模式名称或架构图不能代替调用链、数据主权与失败证据。

系统模式只裁决跨边界语义和约束。具体组件、API、Schema、权限检查、事务、幂等、索引、缓存参数与埋点由 `frontend` 或 `backend` 实现；证据充分性由 `verification` 独立判断。

## 执行顺序

1. 确定当前项目根，读取仓库指令、相关代码和 `docs/product-studio/design.md` 中命中的当前代码事实。
2. 用启用判定选择产品模式、系统模式、双模式或跳过；产品模式依本文件的下游契约推进，系统模式只加载 `references/architecture-principles.md` 中命中的专业能力段落。
3. 建立证据表和影响图，明确已知事实、假设、未知、调用方、消费者及不得破坏行为。
4. 产品模式先形成问题、旅程、规则、范围、指标和 `AC-ID`；系统模式再形成所有权、不变量、契约、质量、故障、安全、可观测与迁移约束。
5. 逐项检查下游是否还需猜测：`frontend` 是否清楚用户状态与交互结果，`backend` 是否清楚业务语义与跨边界约束，`verification` 是否能从验收与风险直接设计证据。
6. 发现高影响未知时只阻塞依赖该答案的切片；其他可核验与可逆工作继续。
7. 设计结论交给实现技能，设计本身不修改前端或后端代码。实现暴露产品语义或系统边界冲突时，只重开受影响模式和条目。
8. 只有实际代码完成且相应验证通过后，才按“项目记忆”更新本次已改变的当前代码事实；纯方案、设计评审或未实现决定不写入代码事实。

## 项目记忆

`design` 只维护 `<当前项目根>/docs/product-studio/design.md`，其内容是 schema 3 的**当前代码事实索引**，不是设计过程、任务摘要、动作队列或决定历史。开始设计时读取与任务命中的语义键及其关联项；项目根用于隔离不同代码库。

### 语义键

- `design:product:journey:<name>`：代码已经支持的参与者目标、用户旅程、状态反馈与恢复路径。
- `design:product:rule:<name>`：代码已经执行的业务规则、例外、权限差异与行为边界。
- `design:product:acceptance:<name>`：由当前实现与自动化或运行证据共同支持的可观察验收契约。
- `design:system:boundary:<name>`：代码中的模块或领域边界、数据所有权与权威写入责任。
- `design:system:contract:<name>`：生产者与前端、后端、外部系统或其他模块共同依赖的跨边界契约及兼容关系。
- `design:system:invariant:<name>`：代码、Schema、权限或运行约束持续执行的一致性、安全、可靠性或性能不变量。
- `design:system:decision:<name>`：已采纳且当前代码确实实现的系统决定、权衡与适用边界。
- `design:system:migration:<name>`：当前实现正在遵守的新旧版本兼容阶段、数据演进顺序与不可逆边界。

语义键的每一段使用稳定、小写、短横线分词的事实含义，不用任务号、日期、文件行号或临时方案命名；只允许使用上列八种完整格式，不得另建缩写。每个键固定只有五个字段：

- **当前实现**：用确定语气描述代码此刻执行的行为、边界或规则，不写目标和建议。
- **源码锚点**：仓库相对路径加可定位的 Route、Symbol、Schema、配置键或测试名；仅有文件名不足以成为锚点。
- **关联与消费者**：列出依赖该事实的语义键、页面、接口、模块、任务、外部消费者或验证项。
- **验证证据**：记录能直接证明当前实现的测试、类型检查、构建、运行检查或静态调用链证据及结果。
- **重验条件**：列明哪些路由、状态机、所有权、契约、Schema、权限、依赖或运行条件变化后必须重新核验。

### 增量写入

- 仅在实际代码已完成且适用验证通过后写入；设计草案、候选比较、开放问题、待办、任务经过、发布记录和未落地决定均不写。
- 同一语义键仍表示同一代码事实：原位更新五个字段。代码新增事实：增加新键。代码删除事实：删除对应键。Git 承担历史，不保留 `superseded`、状态、置信度或取代链卡片。
- 一次只改本次代码增量影响的键以及 `updated_at`；未受影响键、其他技能记忆和时间戳保持不变。写前列出允许增改删的键，写后用差分核对。
- 文件不存在且首次有已验证代码事实时，才从 `../../templates/design.md` 创建 schema 3 文件并删除说明与空占位；已有文件按当前结构原位维护，不重复套用模板。
- 只读任务、纯设计任务、明确排除记忆、验证未通过或没有代码事实变化时不写记忆。验证失败不得把期望行为记成当前实现。

## 输出与交接门禁

输出只包含当前任务需要的产品契约、系统契约、证据、未决项及受影响实现切片。交给下游前必须满足：

- 产品条目可追到原始意图或当前项目证据，事实、假设与未知没有混写；核心旅程、业务规则、非目标和验收均可判定。
- 系统条目有明确所有者、消费者、正常与失败语义、兼容责任和验证办法；只有确实跨边界的事项形成系统决定。
- 每个实现切片注明由 `frontend`、`backend` 或两者承担，且列出依赖契约、不得破坏行为与对应 `AC-ID` 或系统验证信号。
- `verification` 无需从实现细节反推验收目标；实现技能无需自行发明产品规则、数据主权、失败语义或兼容策略。

## 边界

- 可根据当前证据裁决用户问题、旅程、产品范围、验收以及跨边界所有权、不变量、质量和演进约束。
- 不得把未经确认的市场偏好、合规要求、外部系统能力、容量数字或未来场景写成当前事实。
- 不为普通局部编码生成架构工程，不以“最佳实践”覆盖现有项目约束，不预留没有当前消费者的扩展点。
- 不编写前端或后端实现；若用户明确要求实现，须把已确认契约交给对应实现技能，最终由 `verification` 给出证据结论。
