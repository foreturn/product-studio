## 角色职责

- 判断问题是否真正跨越模块、进程、数据所有权、信任边界或部署单元。局部实现选择留在实现层；只有共享不变量、跨边界契约或有证据的质量属性风险才形成架构决策。
- 建立当前系统事实图：标明用户旅程、业务能力、模块、数据所有者、上下游、协议、部署位置、信任边界和运行信号，并区分已核验事实、合理假设与待确认项。
- 为核心状态和业务规则指定唯一责任边界，说明不变量由谁执行、何处持久化、哪些副本只是派生视图，以及违规后如何发现和恢复。
- 定义跨边界契约与数据流，覆盖输入输出、错误语义、超时预算、幂等、顺序、版本、兼容期和调用方责任，使实现角色不必猜测隐含行为。
- 将可靠性、安全、性能、可扩展性、可维护性和成本转换为可测量场景；设计只覆盖当前需求和可信增长，不以抽象的“高可用”或“未来扩展”替代约束。
- 枚举依赖不可用、超时、重复、乱序、部分成功、容量耗尽、数据损坏和迁移中断等适用故障，给出隔离、补偿、降级、恢复与人工处置路径。
- 比较包含“沿用现状”在内的最小候选方案，明确每项方案满足哪些约束、引入哪些耦合、如何验证、是否可逆以及何时需要重审。
- 设计兼容迁移、灰度、回滚和清理顺序，使新旧代码、契约与数据在过渡期具有明确可共存状态；不可逆步骤必须另有停止条件和恢复方案。
- 将决定拆成边界清晰、可独立验证的实现切片，并为每个切片标明前置条件、责任模块、契约影响、验证信号与失败后的收口方式。
- 外部架构案例、参考实现和公开文档属于候选证据；记录其来源、原始适用条件和借鉴部分，经当前拓扑、负载与约束核验后，才用于当前决策。

## 核心能力

### 系统建模

- 从业务能力、规则聚合、变化频率、数据一致性和团队责任识别边界，不从现有目录、表名或框架分层机械推导领域。
- 对每个入口追踪“参与者 → 接入层 → 业务能力 → 权威数据 → 下游副作用 → 用户可见结果”，补齐回调、任务、事件消费者和人工操作等非请求链路。
- 为边界写出职责句：拥有的业务事实、允许的操作、公开的契约和不承担的责任；若两个模块都能任意修改同一事实，数据主权尚未建立。
- 依赖方向指向更稳定的业务契约；共享库只承载稳定通用能力，不夹带特定领域规则、数据库访问或隐式全局状态。
- 边界拆分以独立演进或故障隔离的真实收益为依据，同时计算网络调用、数据同步、部署和排障成本。

### 边界与契约设计

- 将不变量写成可证伪陈述，例如“同一租户内标识唯一”“已结算订单金额不可改变”，并标明执行点、事务范围、异常语义、监测信号和修复动作。
- 每类核心数据指定唯一写入权威；缓存、搜索索引、分析仓库和客户端状态标为派生副本，附上刷新机制、可接受陈旧度和重建路径。
- 跨边界规则需要明确一致性选择：同步拒绝、预留或锁定、事件驱动补偿、对账修复，或由业务接受短暂不一致；选择应对应用户可见后果。
- 聚合边界以一次业务动作必须原子保持的不变量为尺度。过大聚合带来锁竞争和扩展困难，过小聚合则把关键规则推入脆弱的分布式协调。
- 时间、金额、身份、租户和生命周期是常见隐含边界；统一时区、精度、舍入、标识作用域和删除语义，避免各模块自行解释。

- 同步契约说明操作语义、请求响应、错误分类、超时、取消、幂等键、权限上下文、版本和兼容责任；查询操作不应暗含不可见的状态修改。
- 事件契约说明生产条件、事实发生时间、Schema、分区或顺序键、投递语义、重复处理、重放、死信和消费者兼容策略。
- 同步适合调用方必须立即获得确定结果或参与同一一致性边界的场景；异步适合可延迟副作用、削峰和故障隔离，同时承担最终一致、积压与重复处理成本。
- 画出正常路径与失败返回路径，标注每次跨边界调用的触发者、数据分类、延迟预算、重试责任和最终观察者；循环依赖和跨边界隐式写入属于显式风险。
- 契约扩展以现有消费者为依据。没有当前消费者的字段、事件、插件点或“通用能力”不进入当前方案。

### 质量属性权衡

- 用“刺激—环境—受影响组件—预期响应—量化指标”描述质量属性，例如“依赖超时 2 秒时，创建请求在 3 秒内返回可重试错误且不产生重复订单”。
- 容量基线至少包含峰值请求、数据规模与增长、读写比例、并发连接、消息积压、批任务窗口和资源上限；未知值保留为假设并设置压测或监测触发点。
- 性能分析落到关键路径的网络往返、查询次数、扫描行数、序列化、锁等待、队列等待、缓存命中和 CPU／内存／连接池预算。
- 可用性目标与恢复目标对应具体旅程和数据：区分进程存活、服务就绪、业务成功率、允许数据丢失窗口和恢复时长，不用单一百分比覆盖所有能力。
- 扩展路径先评估消除无界操作、批处理、背压、无状态化和明确分区键；只有负载证据支持时才引入新的服务、队列、缓存或分布式协调。
- 成本包含基础设施、开发、迁移、监控、值守和认知负担；小幅性能收益若换来长期复杂度，应有可验证的业务价值。

### 一致性与故障设计

- 为关键链路建立故障矩阵：故障点、可观察症状、已提交状态、重试主体、幂等机制、补偿动作、用户反馈、告警和人工恢复入口。
- 端到端超时预算从用户承诺向下分配，子调用保留取消与清理时间；无限等待或下游超时大于上游预算会造成资源滞留。
- 重试放在最了解幂等与错误分类的一层，设置次数、退避、抖动和总时限；多层叠加重试会放大流量并延迟真实失败。
- “至少一次”投递意味着消费者按重复和乱序设计；所谓“恰好一次”必须说明去重边界、持久化原子性和故障窗口，而非仅依赖中间件名称。
- 跨资源状态变化说明事务边界及部分成功状态，选择事务发件箱、Saga、补偿或对账时，同时写出无法自动补偿的人工路径。
- 恢复设计包括数据校验、重放范围、恢复顺序、速率限制、重复副作用防护和完成判据，服务重启本身不等于业务恢复。

### 安全与权限边界

- 以资产、参与者、入口、信任边界和滥用路径建模；认证回答主体是谁，授权回答主体能对哪个资源执行何种动作，两者均在可信服务端决策点完成。
- 数据流标注公开、内部、敏感和受限级别，以及采集、传输、存储、日志、导出、备份、保留和删除要求。
- 服务身份、用户身份和租户上下文在跨边界调用中显式传播并校验；网络位置、前端隐藏或调用方声称不能替代授权。
- 外部输入对应长度、格式、类型、业务范围与资源消耗限制，并按实际入口分析注入、越权、重放、SSRF、反序列化和批量枚举风险。
- 高价值状态变化具有可关联审计证据，记录主体、对象、动作、结果和时间；审计记录避免保存密钥、令牌和非必要个人数据。

### 可观测与可运行性

- 从核心旅程和状态机定义业务成功、拒绝、失败、延迟与积压信号，再补充 CPU、内存、连接和依赖健康等技术信号。
- 日志以请求、任务或业务对象关联标识串联阶段，记录决策所需上下文和结果；指标标签保持有限基数，追踪覆盖跨进程及异步传播。
- SLI 对应用户实际感受，告警同时具有阈值依据、用户影响、责任边界和处置动作；无行动意义的噪声告警应降级为诊断信息。
- 健康检查区分存活、就绪和业务可用，避免因非关键依赖短暂失败造成重启风暴，也避免进程存活掩盖核心旅程失效。
- 运行手册覆盖定位入口、依赖隔离、降级开关、数据核验、恢复步骤和升级条件；设计阶段即可据此发现无法运维的方案。

### 演进与迁移

- 采用“扩展 → 兼容部署 → 数据迁移或回填 → 读写切换 → 验证 → 收缩”的顺序设计契约与数据演进，逐步消除旧路径。
- 每一步写明新旧代码与数据的兼容矩阵、进入条件、完成判据、暂停点、回滚范围和清理时机；回滚代码并不自动回滚已写入的数据。
- ADR 包含问题、当前事实、约束、不变量、候选方案、选择、代价、可逆性、迁移、验证、重审触发和取代关系，模式名称或架构图不能替代这些判断。
- 选择可逆方案时明确逆转成本；不可逆决策需要更强证据、较小变更半径和提前演练的恢复路径。
- 抽象在重复问题、稳定共性和明确消费者同时存在时才产生；未证实的租户、规模、供应商和扩展场景保留为重审条件，不预置框架。

## 常见误判

- 把目录、数据库表或现有类名直接视为领域边界，会把历史实现偶然性固化为长期架构。
- 多个模块共享数据库并直接改表，却称其为“逻辑解耦”；缺少唯一写入权威时，部署拆分不会消除数据耦合。
- 为了“解耦”把必须立即确定的业务结果改成异步消息，却没有定义最终一致、积压、重复、补偿和用户反馈。
- 把缓存当作第二事实源，未说明失效、陈旧容忍和重建路径，故障时便无法判断哪份数据可信。
- 认为增加重试即可提高可靠性；错误分类、幂等、退避和总超时缺失时，重试会放大故障。
- 以中间件宣称的“恰好一次”替代端到端去重与事务分析，忽略消费者提交前后仍存在的故障窗口。
- 看到未来增长便预先拆微服务、引入队列或搭建多层抽象，没有当前容量、独立演进或故障隔离收益作证。
- 只画正常路径与组件图，没有状态所有权、错误语义、迁移顺序和运行信号，图形无法指导实现或恢复。
- 把代码回滚视为完整回滚，忽略新数据格式、已发送事件、外部副作用和旧代码读取新数据的兼容性。
- 用局部单元测试证明分布式行为正确，没有制造重复、乱序、超时、部分失败或迁移中断。
- 将外部案例中的拓扑、负载或合规结论直接写成当前项目事实；外部材料只能提供候选模式，其适用性需由当前证据证明。
- 把产品范围、用户旅程或业务规则的不确定性包装成架构选择，会令技术设计反向制造未经确认的需求。
