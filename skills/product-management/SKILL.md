# 产品管理

把模糊诉求收敛为可追溯、可取舍、可验收的产品契约。关注为何做、为谁做、做什么、做到何处以及什么算成；不以长篇计划替代事实，也不设计用户界面或技术实现。

## 唯一决策权

`product-management` 是下列语义的唯一 Owner：

- 目标用户、利益相关者及其优先关系；
- 待解决问题、期望用户结果与业务价值；
- 产品层业务政策、资格、状态含义与例外；
- 当前增量的范围、优先级、非目标和不得破坏行为；
- 产品假设、成功指标及产品层验收语义。

体验入口、旅程、内容和用户可见状态属于 `product-experience`；系统边界属于 `software-architecture`；接口、数据、前端和安全机制分别属于相应工程专业。相邻专业可以提供事实与约束，但不能静默改写上述产品决定。

## 输入与停止条件

开始判断前，确认并核验：

- Git 仓库根、当前产品、稳定 `product-id`、相关项目根和仓库指令；
- 用户原始请求、真实产品入口、现有行为、直接使用者与受影响角色；
- 相关代码、配置、契约、测试、运行证据及已有产品事实；
- 已明确的限制、不得破坏行为、合规承诺和风险承受边界。

将材料逐项标为用户裁决、仓库事实、运行证据、权威外部约束、合理假设或未知。可从当前仓库和产品自行查明的事项直接核验，不向用户转嫁调查工作。

缺少下列任一契约且该缺口会实质改变决定时，停止受影响判断并列明：缺少什么、为何阻塞、可接受的权威来源、哪些判断仍可继续：

- 无法确定目标用户、期望结果或问题边界；
- 业务资格、强制政策或合规义务相互冲突；
- 范围选择涉及不可逆结果但没有裁决依据；
- 成功口径或验收语义存在多个互斥解释；
- 当前产品或 `product-id` 无法唯一确认。

局部、可逆且不改变用户结果的未知可以假设继续，但必须记录来源、置信度、失效条件和验证办法。

## 具体方法

### 1. 定义问题

1. 从真实入口复现或追踪现行路径，记录触发条件、当前做法、阻碍位置、替代办法和失败代价。
2. 将用户给出的方案改写为待验证的问题陈述，避免把“增加按钮”“新增页面”等实现主张直接当作需求。
3. 使用以下句式收口：`<角色> 在 <触发场景> 需要 <期望结果>，当前因 <可观察阻碍> 无法或高成本完成，造成 <影响>`。
4. 附上事实依据；无法证实的频率、损失或因果关系明确标为假设。

### 2. 建模用户与利益相关者

1. 识别直接使用者、发起者、审批者、数据所有者、运营者、结果接收者和被影响者。
2. 仅当目标、任务、政策资格、接收结果或失败后果不同才拆分角色，不照搬数据库角色或组织架构。
3. 对每个角色记录目标、触发、责任、可见结果、失败后果和与其他角色的冲突。
4. 出现冲突时，以明确的产品目标、法律义务、风险和主要结果裁定优先关系；没有依据时保留待决，不求虚假共识。

### 3. 建立价值与结果链

1. 从拟提供的能力向后追踪到行为变化、用户结果和业务结果。
2. 分开结果与产出：功能上线、页面数量和按时交付不是用户或业务结果。
3. 为每一环标出可观察信号、归因限制、潜在副作用和不得牺牲的质量护栏。
4. 删除无法影响当前结果、没有真实消费者或只为未来设想预留的范围。

### 4. 裁定产品政策

1. 以业务语言定义对象、角色资格、前置状态、允许动作、拒绝原因和结果状态。
2. 明确重复、撤回、过期、部分完成、人工介入和跨入口一致语义中实际存在的情形。
3. 对每项政策记录权威依据、适用范围、例外、受影响结果和冲突来源。
4. 只描述业务应当发生什么，不规定鉴权算法、数据库锁、API 字段或其他技术机制。

### 5. 划定范围与优先级

1. 先写出能够产生完整用户结果的最小闭环，再区分必要完整性、可延后项和非目标。
2. 按用户价值、风险降低、依赖事实、学习价值、可逆性和验证成本排序。
3. 每个纳入项说明为何现在必须有；每个排除项说明不会破坏哪项核心结果。
4. 把现有能力、兼容关系和明确不得退化行为列为范围护栏。

### 6. 管理假设与风险

1. 用“假设内容、来源、置信度、影响、可逆性、失效条件、验证方式”登记未知。
2. 高影响、低可逆或涉及合规的假设不得伪装成决定；给出互斥选项及其结果差异。
3. 选择能改变决定的最小调查或实验；无论结果如何都不会改变决定的验证不应开展。
4. 新证据出现时只重审受影响的产品语义，并明确其余决定为何仍成立。

### 7. 定义成功指标

1. 分别选择用户结果指标、业务结果指标和副作用护栏，检查当前增量是否能合理影响它们。
2. 写清指标对象、口径、分子分母、时间窗口、分群、基线、目标或判断阈值、数据来源和异常解释。
3. 没有基线时写“待建立基线”及采集办法，不制造精确数字。
4. 无法采集或无法归因的宏大收益只能作为方向，不得作为当前增量的通过条件。

### 8. 编写验收契约

1. 为每项独立结果分配稳定 `AC-ID`，保持编号不随实现文件变化。
2. 使用“给定前置条件—执行用户或业务动作—观察结果—禁止结果”描述验收。
3. 覆盖适用的角色资格、成功、拒绝、失败恢复、重复操作和不得破坏行为。
4. 只写用户或业务可观察语义；除非技术约束本身就是已确认产品承诺，否则不绑定组件、接口字段或存储实现。
5. 为每条验收标明证据入口、环境边界和仍未覆盖的风险。

### 9. 保持决策追溯

1. 为问题、政策、范围、指标和 `AC-ID` 记录权威依据、采用理由、直接消费者、失效条件与复核触发。
2. 建立最短映射：原始意图 -> 产品决定 -> `AC-ID` -> 可观察证据。
3. 决定改变时原位更新当前语义，明确受影响与不受影响项；Git 负责保存历史。
4. 不把讨论流水、备选草稿或实施过程混入最终产品契约。

## 输出格式

- **产品问题**：角色、触发场景、当前差距、期望结果、失败代价、业务价值和依据强度。
- **用户与价值**：角色关系、冲突优先级、能力到用户结果及业务结果的因果链和护栏。
- **产品政策**：业务对象、资格、前置状态、允许与拒绝语义、结果状态、例外和适用范围。
- **范围决定**：核心闭环、必要完整性、优先级、非目标、不得破坏行为及取舍理由。
- **假设与指标**：假设登记、风险等级、验证办法、成功口径、基线或待建基线。
- **验收契约**：`AC-ID`、前置、动作、可观察结果、禁止结果、证据入口和环境边界。
- **决策追溯**：权威依据、采用理由、直接消费者、失效条件和复核触发。

## 当前产品事实

产品管理事实的稳定 locator 为 `<Git仓库根>/docs/product-studio/<product-id>/design.md`，不因 Skill 名称变化而迁移，也不得另建 `product-management.md` 复制同一事实。只有已经由当前实现、权威契约和相称验证证实的当前事实才可写入；具体收录、格式、变更与权限规则见 [产品管理事实规则](references/memory.md)。

## 完成标准

- 问题、角色、结果、政策、范围、指标和验收之间没有相互冲突；
- 高影响未知已被裁定、显式阻塞或作为有边界假设登记；
- 每项范围都能追溯到当前价值、风险或必要完整性；
- 每条 `AC-ID` 都有可观察结果、禁止结果和可取得的证据入口；
- 相邻专业所有权清晰，产品决定没有夹带体验或技术实现；
- 结论足以让实现者不再猜测产品意图，但不宣称代码或整个增量已经完成。

## 禁区

- 不裁定页面入口、信息层级、文案、交互顺序、响应式或无障碍体验。
- 不裁定系统边界、API 字段、错误码、Schema、索引、事务、组件、视觉令牌或实现代码。
- 不把竞品做法、市场传闻、未经核验的合规要求、未来设想或无基线精确指标写成当前决定。
- 不为没有当前价值、风险或消费者的场景预建范围，不以实现容易代替价值与风险排序。
- 不以产品验收措辞反向规定无关技术方案，不用产品分析代替实现和验证证据。
