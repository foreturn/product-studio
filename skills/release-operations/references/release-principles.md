# 发布与运行能力准则

## 授权、范围与制品

- 区分发布方案、就绪检查和实际部署；只有明确授权才产生外部状态变更。
- 固定待发布版本、提交、构建、依赖、配置和迁移，确保制品可追溯到已验收实现。
- 明确目标环境、租户或用户范围、时间窗口、责任人、依赖和禁止包含的改动。
- 复用现有 CI/CD 与运维工具，不为一次发布另建未经验证的平台或旁路命令。

## 发布策略

- 低风险且易回滚的变更可直接或滚动发布；高风险、用户影响大或不确定的变更优先灰度、蓝绿或功能开关。
- 每个批次定义进入条件、覆盖范围、观察窗口、成功阈值、停止条件和下一步。
- 功能开关说明默认值、权限、生命周期和清理时间，避免永久残留双路径。
- 发布顺序考虑前后端兼容、依赖就绪、缓存、任务和数据迁移，避免新代码先依赖尚未存在的结构。

## 配置、密钥与环境

- 环境配置与制品分离，明确必需变量、默认值、来源和敏感级别；禁止把生产密钥写入仓库或日志。
- 发布前比较环境差异、权限、容量、网络、时区和第三方依赖，不假设测试环境等同生产。
- 配置变更可审计、可回滚并有生效验证；需要重启或滚动刷新时写明顺序与影响。

## 数据与迁移

- 采用先扩展、再迁移、后收缩的兼容顺序，使新旧版本在发布窗口内都能工作。
- 评估锁、事务时长、日志、存储、回填批次、双写、复制延迟和失败重试。
- 迁移脚本可重入、可观察、可暂停；运行前备份或验证恢复方案，运行后核对数量与业务不变量。
- 回滚不仅回退代码，还要说明数据、配置、消息和外部副作用如何处理。

## 可观测性与上线验证

- 同时观察基础设施、进程、依赖、应用错误、延迟、吞吐、队列和核心业务成功信号。
- 为关键指标记录发布前基线、阈值、观察方式和责任人；关注趋势与用户影响，不只看瞬时绿灯。
- 健康检查区分存活、就绪和业务可用；进程存活或 HTTP 200 不能独自证明产品成功。
- 发布后实际走完核心旅程及重要失败或恢复路径，确认新旧功能、权限和数据结果。

## 停止、回滚与事故

- 预先定义错误率、延迟、数据异常、业务失败或支持反馈等停止条件，触发后停止扩大范围。
- 回滚步骤必须包含负责人、命令、顺序、验证、数据处理和无法回滚时的缓解方案。
- 事故中先限制影响、保存日志指标和时间线，再回滚或升级；不要临时加入未经评估的新改动。
- 恢复后记录根因、发现缺口、处置效果和防复发措施，区分代码、配置、流程和监控问题。

## 反馈与迭代

- 汇总运行指标、用户行为、客服问题、错误样本和业务结果，区分缺陷、体验摩擦、运营问题与新需求。
- 反馈记录来源、频率、影响用户、严重程度和现有证据，不以单个声音直接扩大产品范围。
- 将需要改变用户旅程、范围或验收标准的内容交回产品角色，形成下一轮最小可验证增量。
