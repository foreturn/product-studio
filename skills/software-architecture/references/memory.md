# 软件架构项目记忆

## 使用方式

项目事实位于 `docs/product-studio/<product-id>/software-architecture.md`。

- 先根据用户范围、产品入口与元数据、相关项目根、目标代码和调用链唯一确认目标 Git 根与 `product-id`；`product-id` 必须在仓库内唯一、稳定，且是非 `.` 或 `..`、不含 `/` 或 `\` 的安全单级目录名。归属不唯一或名称不安全时不猜测或创建事实册。
- 开始相关工作前读取已有事实。
- 当前代码、配置和正式契约等权威信息与旧事实冲突时，以当前权威为准。
- 只按下列主题记住会持续影响后续判断且难从局部代码直接看清的项目不变量，不复制源码、配置或可生成清单。
- 核心认知改变时更新或移除旧内容，只保留当前仍成立的事实。
- 不记录秘密、用户数据、任务过程和一次性结果。

## 核心记忆

### 系统职责与边界

- 记住各系统、服务和核心模块实际承担与明确不承担的职责，以及边界的业务理由。
- 记住跨越边界时的信任、所有权和变更责任，尤其是不能从目录结构直接看出的划分。

### 模块依赖与稳定契约

- 记住模块之间允许的依赖方向、禁止的反向依赖和必须保持稳定的跨模块契约。
- 记住真实消费者依赖的扩展点、替换边界与兼容约束。

### 数据权威与一致性

- 记住每类关键数据的唯一权威、派生副本和缓存分别由谁维护。
- 记住跨边界同步的一致性保证、冲突裁决、允许陈旧范围和修复责任。

### 跨边界交互

- 记住关键调用采用同步、异步或批处理的既定关系，以及选择该关系所保护的系统性质。
- 记住身份与上下文传播、顺序、重复处理、超时和失败隔离中必须维持的保证。

### 运行拓扑、故障与恢复

- 记住运行单元、通信关系、状态位置和故障域，以及哪些故障会跨边界传播。
- 记住降级、重启、接管和恢复时各组件承担的责任与不能自动恢复的边界。

### 质量权衡、演进与守卫

- 记住项目已经作出的关键质量取舍、适用条件，以及不得被局部优化破坏的优先级。
- 记住架构演进允许改变与必须保持兼容的部分、不可逆约束，以及阻止边界腐化的项目机制。
