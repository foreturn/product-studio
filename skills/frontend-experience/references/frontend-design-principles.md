# 前端设计与用户体验能力准则

## 易用性与任务效率

- 先确定用户此刻最重要的任务，让主路径在首屏可发现，主操作明显且每个局部区域尽量只有一个视觉主按钮。
- 删除不产生价值的步骤、重复输入和确认；利用已有数据、合理默认值、自动保存或继承减少操作成本。
- 高频功能直接可达，低频和高级功能通过菜单、抽屉、标签页或渐进披露进入，不让所有选项同时争夺注意力。
- 危险且不可逆的操作才使用确认；可逆操作优先提供撤销。失败后保留用户输入与上下文。
- 表单按用户理解顺序分组，使用明确标签、就近校验和可执行错误提示，不依赖占位符充当标签。
- 用户无需阅读功能说明才能完成核心任务；界面通过层级、控件和反馈自然表达用法。

## 信息架构与内容组织

- 围绕用户动作和业务目的组织导航、标题、分组和表格，不按后端模块或数据库字段排列界面。
- 建立从页面标题、区块标题、正文、辅助信息到元数据的稳定层级，扫描顺序应与任务顺序一致。
- 相关内容靠近并共享对齐，不相关内容通过留白、分隔或不同区域区分；不要用大量卡片替代清晰结构。
- 长列表、历史和明细使用分页、筛选、分组、固定表头或分视图，避免无限堆叠和横向信息过载。
- 文案回答当前状态、可执行动作和下一步；按钮使用“保存”“去支付”等任务词，不暴露接口名、枚举或供应商实现。

## 布局与响应式

- 使用一致的容器宽度、网格、对齐线和间距尺度；相同层级保持相同内外边距，避免随手填写的零散尺寸。
- 根据内容选择稳定布局：工具栏、表格、棋盘或固定格式控件应声明网格轨道、最小宽度、宽高比或稳定尺寸。
- 控制阅读宽度和信息密度；运营工具偏紧凑可扫描，内容阅读区偏舒展，不把展示级大字放进紧凑面板。
- 小屏优先保留主任务与关键信息，再调整列数、顺序或交互形式；不要只把桌面布局等比缩小。
- 检查长标题、长单词、数字、状态标签和按钮文案，确保换行、截断或动态尺寸合理，无溢出、遮挡和布局跳动。
- 避免用视口宽度直接缩放字体；通过断点、容器约束和内容重排适配不同尺寸。

## 交互与状态反馈

- 每次点击、提交、切换和拖动都应有即时反馈；异步动作提供加载、禁用、防重复提交、成功或失败结果。
- 为加载、骨架、空白、部分成功、权限不足、网络错误、数据过期和恢复设计明确状态，避免只有快乐路径。
- 返回、取消、关闭和刷新不得意外丢失关键上下文；多步骤流程显示当前位置、已完成内容和可返回范围。
- 控件匹配任务：图标用于熟悉工具，开关用于即时二元设置，复选框用于多选，单选或分段控件用于互斥模式，菜单用于较长选项集。
- 图标按钮提供可访问名称和必要提示；不要用带文字的圆角矩形替代用户熟悉的保存、撤销、下载等图标。
- 动画只用于解释状态变化、空间关系或反馈，时长克制并支持减少动态效果，不以动画掩盖延迟。

## 色彩、排版与视觉协调

- 先沿用现有设计令牌；没有设计系统时，定义中性色、品牌强调色、成功、警告、错误、信息与焦点等语义角色。
- 中性色承担大面积背景和正文，品牌色用于主动作和关键强调，状态色只表达对应语义；不要让多个高饱和颜色同时成为主角。
- 同一状态使用一致颜色、图标和文案，且不能只靠颜色传达含义；为色觉差异补充文字、形状或图标。
- 检查正文、次要文字、边框、禁用态、焦点与状态色在实际背景上的对比度，不用过浅灰色隐藏重要信息。
- 正文文字对比度 ≥ 4.5:1，大号文字（≥18pt 或 14pt 粗体）≥ 3:1；关键交互态与重要信息不得低于此 WCAG 基线。
- 使用有限且稳定的字号、字重与行高层级；正文保证可读，紧凑控件使用合适字号，不使用负字距或无意义超大标题。
- 图标风格、描边、尺寸和对齐保持一致；优先复用项目已有图标库，不混用多套视觉语言。
- 避免单一色相统治整个界面，也避免无业务意义的渐变、光斑、装饰球和过多阴影；视觉强调必须服务层级。
- 卡片只用于真正独立、重复或需要边界的对象，不把页面所有区块做成悬浮卡片，也不嵌套卡片。

## 可访问性

- 使用正确的语义元素、标题顺序、表单标签、按钮和链接，不以无语义容器模拟交互控件。
- 确保键盘可完成核心旅程，焦点顺序符合视觉顺序，焦点状态清晰且不会陷入弹窗或隐藏区域。
- 为图片、图标、状态变化和动态通知提供适当替代文本或辅助技术提示。
- 交互目标在触控和鼠标环境中都易于命中，避免只有悬停才能发现的关键能力。
- 可点击区域至少约 44×44px，相邻目标留足间距以防误触；移动端关键操作优先满足此尺寸基线。
- 对错误给出字段关联、原因和修复动作；对加载和异步结果使用适当的可访问状态通知。

## 状态建模与组件工程

- 状态建模：将远程数据、表单、导航和瞬时交互状态分开建模，避免多个布尔值组合出不可解释状态。
- 复用现有组件和设计令牌；只在稳定共性已经出现时抽象，不为单个页面建立新的通用组件体系。
- 组件职责围绕业务表达与交互边界，避免巨型页面组件，也避免把简单结构拆成过多转发组件。
- 处理请求取消、竞态、重复提交、乐观更新回滚、错误边界和会话过期等真实运行情况。
- 控制包体、图片、字体、渲染次数和长列表成本；性能优化应以测量和用户影响为依据。
- 以 Web Vitals 作为体验基线参考：LCP < 2.5s、INP < 200ms、CLS < 0.1；未达标时先定位瓶颈再优化，不以猜测代替测量。

## 真实验收

- 在代表性桌面与移动视口走完核心旅程，检查初始、加载、空白、错误、成功和恢复状态。
- 检查文本是否溢出、控件是否移动、内容是否重叠、弹层是否被裁切、滚动区域是否合理、触控是否可用。
- 通过键盘走查焦点、表单和弹层；检查颜色对比、辅助名称和减少动画行为。
- 查看控制台错误、失败网络请求、资源加载和运行警告；类型检查通过不能替代浏览器验证。
- 对画布、图表、3D 或关键媒体检查实际像素与资源加载，不能只确认 DOM 节点存在。
