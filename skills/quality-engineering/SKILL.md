# 质量工程与独立验收

从用户原始意图、当前专业契约和完整差异建立独立验收标准，不以实现现状倒推成功。只有每项适用必需标准都获得匹配当前修订、环境、输入与断言的直接证据，才能判定通过。

## 专业所有权

`quality-engineering` 唯一裁定验证策略、风险优先级、证据层级、测试与夹具设计、缺陷归因状态、退出条件，以及当前修订的通过、失败、阻塞或不适用结论。

产品、体验、架构、API、物理数据库、安全、发布政策及运行健康是验收输入，不由质量工程补写或降低。验收结论只证明其绑定的修订、制品、环境和要求，不等于事实已同步、制品已发布或生产环境健康。

## 输入与证据门槛

- 明确 Git 仓库根、当前产品与稳定 `product-id`、相关项目根、仓库指令、授权范围、待验收修订或制品、比较基线、完整差异、目标环境、身份、数据、已知既有失败和停止位置。
- 固定用户原始意图、范围、业务不变量、体验契约、架构决定、API 与数据契约、安全控制、迁移约束和适用验收标准；将来源区分为用户要求、仓库事实、已接受决定、假设、推断或未知。
- 缺失或矛盾的权威要求不得从实现、测试名称、快照或旧报告反推。只阻塞依赖该要求的检查，并写明缺口、影响范围、所需裁决和可继续部分。
- 验证限于本地、测试夹具或明确授权且隔离的测试环境；未获精确授权时不得执行生产写入、生产迁移、远端发布或其他外部状态变化，结论不得外推到未取证环境。

## 验证方法

### 1. 固定验收对象与追溯矩阵

1. 记录仓库、基线、目标修订或制品摘要、工作区状态、配置、环境、身份、数据和时间边界；对象任一漂移时，受影响证据失效并重新取证。
2. 将每项要求写成可证伪检查：稳定 ID、来源、前置、输入、动作、预期结果、禁止结果、适用环境、证据入口和失效条件。
3. 建立“要求 -> 实现位置 -> 检查 -> 当前证据 -> 结论”追溯；没有要求的改动标为范围疑点，没有实现或证据的要求标为缺口。

### 2. 建模风险与回归半径

1. 检查完整差异、调用链、共享依赖、消费者、配置、API Schema、数据库制品、安全边界、迁移与运行影响，不以文件数代替影响分析。
2. 按影响严重度、发生可能性、可发现性、可逆性、权限扩大、数据敏感度、外部副作用、兼容窗口和历史缺陷排序风险。
3. 为每个高价值风险写明失败模式、触发条件、检测方式和所需证据；优先覆盖静默错写、越权、重复副作用、兼容断裂和不可恢复变化。
4. 局部验证只有在写入集、依赖和消费者均有证据表明局部时才成立；未覆盖风险须写明触发条件、影响对象、发现手段和重验入口。

### 3. 选择证据层级与设计测试

1. 为每项要求选择成本最低且能直接证明它的证据：静态检查证明语法与类型，单元测试证明局部规则，契约测试证明边界，集成与端到端证明协作与用户旅程。
2. 快速检查先行，但不得以格式、构建、覆盖率或测试数量代替高层行为。关键快乐路径至少配一个高价值边界、拒绝、故障或恢复路径。
3. 测试数据覆盖空值、边界值、重复、乱序、过期、权限差异、旧版本、部分成功和代表性规模；时间、随机、网络与并发使用可控时钟、种子、替身、同步屏障或隔离环境。
4. 允许写测试时，先让最小测试因目标行为缺失而失败，确认失败原因正确，再实现或验证修复；只读验收可使用现有测试、探针与操作步骤，但不得伪造持久测试制品。

### 4. 分层执行与直接观察

1. 先运行格式、静态、类型、单元和聚焦契约检查，记录工作目录、完整命令、退出码、首个可行动错误和日志位置。
2. 前端受影响时，从真实入口操作核心旅程与高价值失败或恢复路径，绑定身份、数据、浏览器、视口、输入方式、页面状态、控制台、网络和修订；检查溢出、焦点、名称、错误关联、缩放和触控。
3. 后端、接口或数据受影响时，核对请求响应、错误、权限执行、事务、幂等、并发、消息与最终业务不变量；物理 Schema、约束、索引、锁和迁移必须使用目标数据库及其已确认设计证据。
4. 安全边界受影响时，依据已确认的威胁与控制契约验证身份、授权、输入输出、秘密、隐私、审计和失败行为；扫描结果只是支持材料，不代替高价值攻击路径。
5. 性能、可靠性、兼容性和发布就绪结论须绑定负载、数据量、设备或资源、环境、版本组合、指标、阈值与观察窗；没有基线时只报告测量值与趋势。

### 5. 处理失败与重验

1. 为每个失败记录最小复现、预期、实际、首个可行动错误、影响范围、环境、输入和当前修订，保存可独立复核的原始证据。
2. 归因只能为本次回归、既有问题、环境阻塞、证据缺失或归因未定。既有问题须有改动前证据或明确影响边界；无法证明时不得猜测。
3. 修复后重新运行直接失败、受影响层级与必要回归；不得通过删除测试、弱化断言、降低阈值、改写要求或反复重跑偶然绿色制造通过。
4. 验收者另行获准修改实现时，须保留修改前失败证据，并把修改后的对象视为新修订重新独立验证。

### 6. 逐项与总体裁决

1. 每项检查只能为 `PASS`、`FAIL`、`BLOCKED` 或 `NOT_APPLICABLE`；不适用须写明判据，未执行但适用的必需项只能失败或阻塞。
2. 总体优先级为 `FAIL` 高于 `BLOCKED`，`BLOCKED` 高于 `PASS`；只有所有适用必需项都获得当前直接证据并通过时，总体为 `PASS`。
3. 结论必须绑定要求、修订或制品、环境、关键输入、证据和失效条件；历史报告、其他分支、其他环境与旧制品只能作为参考。

## 输出

- 追溯矩阵、风险排序、验证策略，以及新增或补充的测试、夹具和检查入口；只读任务不强制写测试文件。
- 逐项 `PASS`、`FAIL`、`BLOCKED` 或 `NOT_APPLICABLE` 结果及直接证据，绑定当前修订、环境、关键输入、命令、退出码或制品。
- 总体裁决、未执行项、未覆盖边界、剩余风险和证据失效条件。
- 失败的最小复现、预期、实际、影响、归因状态、所缺专业语义与重验条件；不预设后续由哪个技能处理。

## 完成门槛

- 每项适用必需标准可从来源追溯到实现位置、当前修订、环境和直接证据；每项改动可反向追溯到仍有效的要求。
- 静态、单元、契约、集成、端到端、真实渲染、真实数据库、安全与运行证据各守其证明边界，没有跨层或跨环境外推。
- 未执行项均明确归为失败、阻塞或有证据的不适用；本次回归、既有失败、环境问题、证据缺失和归因未定彼此分开。
- 总体裁决没有冒充事实同步、发布授权、实际部署或生产健康。

## 独立性与禁区

- 可独立选择验证深度、补充测试和夹具、拒绝不匹配证据，并裁定通过、失败、阻塞、不适用、既有问题或归因未定。
- 默认不修改业务实现；另行授权修复也必须保存原始失败证据，并对新修订重新验证。
- 不重新设计产品、体验、架构、数据库或安全策略，不降低验收标准、删除有效测试、弱化断言或反向改写需求来制造通过。
- 不执行未授权的外部状态变化，不裁定生产执行与健康，也不把事实候选直接写成已同步事实。
