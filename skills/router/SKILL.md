# 编码任务网关

本技能只作代码任务路由与跨技能编排，不代替 `design`、`backend`、`frontend`、`verification` 作专业裁决，不保存任何项目记忆。

## 输入

- 用户期望的可观察结果、显式非目标、允许修改的范围与停止位置。
- 当前仓库结构、项目指令、已有改动、受影响模块、现行契约与可用验证命令。
- 用户允许执行的阶段：只读分析、方案设计、代码修改或验证，以及明确的停止位置。

## 专业能力来源

进入本技能后，先读 `references/delivery-capabilities.md` 的“目录”与“核心能力”，完整读取与任务匹配的能力段落。涉及多个技能、共享契约、并行分支、风险门禁或终态归并时，再读取该文件的“常见误判”。该 reference 只保存编排所需的专业能力准则；触发条件、路由规则、记忆边界与外部操作边界以本文件为准。

## 直达与触发

目标和边界明确时，绕过本技能：

- 产品行为、领域边界、跨模块契约或技术方案设计：直接调用 `design`；仅加载其产品模式、系统模式或两者。
- 局部服务端、API、数据访问、权限、缓存、消息或集成实现：直接调用 `backend`；发生代码变化后调用 `verification`。
- 局部页面、组件、交互、视觉、响应式或可访问性实现：直接调用 `frontend`；发生代码变化后调用 `verification`。
- 测试补充、缺陷复现、回归、联调或只读质量审计：直接调用 `verification`。

出现以下任一情形才启用本技能：

- 请求只有愿景或结果描述，尚不能确定产品行为、改动边界或验收口径。
- 同一结果同时跨越 `design`、`frontend`、`backend` 中两个以上专业领域，且存在共享契约或先后依赖。单一实现技能后的常规 `verification` 只是终端门禁，不计作跨领域触发条件。
- 用户要求“完整功能”“端到端”“从零实现”，需要建立最小可运行纵向切片。
- 变更可能影响多个模块、数据所有权、公共 API、权限边界、异步一致性或多个并发写入者。

## 最小调用链

按真实产物缺口选链，不为了形式完整调用全部技能：

```text
明确前端改动       frontend -> verification
明确后端改动       backend -> verification
明确设计问题       design
明确测试或审计     verification
契约清晰的全栈改动 backend + frontend -> verification
模糊或跨边界改动   router -> design -> backend(冻结具体 API 契约) -> backend + frontend -> verification
```

只读分析停在产生所需结论的技能；不得擅自进入实现。仅改一端时不得为了凑齐链路调用另一端。`design` 只在需求或系统不变量尚未确定时加入，不把每个局部实现都升级成架构设计。

## 编排规则

1. 解析当前项目根和适用指令，保留用户原始意图，列出结果、范围、非目标、完成信号和允许执行的阶段。
2. 按 `delivery-capabilities.md` 的专业能力准则归类任务，画出节点、输入、输出、消费者、硬依赖、共享契约、写集合和验证门禁。
3. 选择能闭合当前结果的最小技能链；缺少高影响且无法从仓库查明的产品、安全、数据或跨系统契约决策时再请求用户裁决。
4. 将跨领域目标切成可独立观察、可独立验证且有恢复点的纵向切片；先验证高代价假设，再启动依赖它的实现。
5. 新增或改变前后端接口时，`design` 只固定产品语义、跨边界责任和兼容约束；由 `backend` 或实际契约拥有者先形成具体 API 契约里程碑，明确字段、错误、权限、异步状态、分页和版本，再判断能否并行。满足全部并行条件时才并行调用 `backend` 与 `frontend`：共同上游契约已经定版、输入快照一致、没有硬依赖、写集合不重叠、共享文件有唯一写入者、各分支能独立验证。
6. 任一并行条件不成立时串行推进。Schema 迁移代码与依赖它的新代码、同一共享契约的多个修改者、同一记忆文件的多个写入者不得并行。
7. 下游发现上游契约错误时，停止受影响分支，将新证据交回契约拥有技能裁决；不得在下游建立隐含的第二套字段、状态、权限或错误语义。
8. 每个里程碑先完成聚焦验证，再解锁消费者；最终由 `verification` 按风险覆盖验收、回归与失败路径。

## 并行归并

- 并行分支各自只修改声明的写集合；共享类型、Schema、路由表、锁文件或生成物须指定唯一写入者。
- 共享契约先由 `design` 或契约实际拥有技能形成单一版本，消费者只按该版本实现；契约变化后重新计算受影响节点。
- 归并顺序固定为契约拥有者、后端或前端实现、生成物、`verification`。后进入者不得覆盖先进入者的用户改动。
- 一个分支失败时先冻结依赖它的节点；不依赖该分支且写集合隔离的分支可继续。若共享契约或基础迁移失败，所有消费者均停止。

## 裁决边界

- 本技能可裁决技能选择、依赖顺序、切片粒度、并行条件、门禁状态、失败隔离范围与终态类别。
- 产品范围和用户行为由 `design` 产品模式裁决；领域边界、跨模块契约与质量属性由 `design` 系统模式裁决。
- 服务端实现由 `backend` 裁决，界面与交互实现由 `frontend` 裁决，是否通过由 `verification` 独立裁决。
- 代码权限不等于生产操作授权，生产执行不在本插件范围。
- 不得因调用本技能扩大用户范围、改写无关文件或引入无证据的新架构。

## 终态收口

收口前读取最终差分和验证证据，逐项对照显式需求，并将本轮标记为：

- `完成`：范围内结果已实现，适用验证通过，无未声明阻塞。
- `部分完成`：可独立使用的切片已经通过，未完成切片及影响已明确。
- `阻塞`：缺少不可替代的产品裁决、仓库访问、测试凭据、验证环境或上游契约，且安全替代路径不存在。
- `失败`：实现或验证未通过，结果不能安全交付；记录首个失败点和未执行的消费者。

终态回复必须列出实际调用链、每个切片结果、修改范围、验证命令与证据、失败或阻塞、既有问题及剩余风险。任务完成后，仅协调实际受影响的 `design`、`backend`、`frontend`、`verification` 各自按其契约增量更新同名代码事实；本技能不创建、不读取、不更新任何网关专属事实文件，也不代写专项记忆。记忆写入失败作为独立持久化故障报告，不得倒改已经成立的实现或验证结论。
