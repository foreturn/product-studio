# 后端工程 · 领域与结构

### 领域规则与状态语义

- 领域模型必须表达业务概念、合法行为和不变量，不能由存储结构、传输对象或界面字段反向定义。
- 对象创建后即应满足核心不变量，状态只能通过具名业务行为改变，任意字段修改不能绕过规则。
- 状态语义必须同时说明合法前置、允许变化、拒绝结果和终止条件，状态值集合不能替代转换规则。
- 同一业务规则必须由唯一权威行为在所有服务端入口一致成立，接口、消息、任务和管理操作应复用相同用例或领域公共面，不能各自复制条件并形成规则旁路。
- 业务拒绝、系统失败和并发冲突必须保持不同语义，不能用一个通用异常抹去调用方可采取的不同动作。
- 跨对象规则若无法在一个一致性范围内保证，必须显式表达暂态状态与收敛条件，不能假装为即时不变量。

### 应用分层与模块内聚

- 实现必须延续仓库既有的请求处理、依赖装配、配置、持久化、异步和错误约定；局部需求不得并行引入另一套同类框架或运行模型。
- 会改变领域行为或共享服务能力的实施，必须先从真实入口沿既有调用链追踪到用例、领域状态、持久化、事务边界、外部副作用和可确认结果，定位已有业务能力及受影响消费者；不得因当前接口或样例不同而另建一条只在局部成立的平行业务路径。
- 模块应围绕业务能力和变化原因组织，不能只按控制器、服务、仓储等技术类型横向堆放全部业务。
- 协议适配、用例协调、领域规则和外部机制必须可辨，业务判断不能散落在传输、映射和持久化细节中。
- 依赖应从易变机制指向稳定业务规则，领域逻辑不能要求特定框架、数据库、消息系统或供应商对象才能运行。
- 模块公开面必须最小且使用稳定业务语义，内部实体、查询能力和实现细节不能成为其他模块的隐式契约。
- 抽象只应隔离真实变化或消除已发生且语义一致的重复，不能为单一实现、形式对称或未来猜测增加层次。
- 副作用必须在调用关系中可定位，隐藏写入、全局状态和运行时依赖查找不能掩盖真实行为。

### 代码组织、命名与通用能力复用

- 代码必须先完整交付已确认的业务行为、拒绝语义和故障边界；行为同样完整时，优先选择分支、状态、层次和运行机制最少且可直接读懂的实现，不为缩短代码省略必要约束。
- 业务能力复用必须以共同不变量、状态转换、拒绝与故障语义为单位，由接口、消息、任务和管理入口调用同一用例或领域公共面；仅把样例值改成参数、抽取工具函数或复制分支，不能替代统一能力所有权。
- 包、目录与文件应按业务能力、职责和变化原因归类并沿用仓库命名惯例；仅服务特定领域的规则不得进入无边界的通用工具目录，物理位置不能隐藏真实所有者。
- 类型与类名称应表达领域概念或明确适配角色，方法与函数名称应表达动作及结果；查询、校验、转换、持久化和外部副作用必须可从名称与调用结构中区分，不能以含混的 `manager`、`processor` 或 `handle` 掩盖职责。
- 常量、配置、状态与行为应由唯一责任模块拥有；魔法值只有形成稳定语义时才抽取，不能建立跨领域常量袋、万能基类或只转发调用的形式化层次。
- 身份、时间、序列化、校验、重试、调度、协议客户端等通用能力，应优先复用项目既有实现、语言或框架标准能力以及维护成熟的开源组件，避免复制源码或重新实现已有机制。
- 引入组件必须核对功能契约、维护状态、安全、许可、传递依赖、资源与运维成本、升级路径和退出代价；只有候选方案无法满足关键要求或总成本更高时才有限自研，并保留可复核理由。
- 对第三方能力只在领域隔离、协议转换或真实替换需求存在时建立适配边界；不得为每个依赖机械包裹一层，也不得让供应商对象、异常和配置扩散为内部公共契约。
