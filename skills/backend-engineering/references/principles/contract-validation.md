# 后端工程 · 契约与校验

### API 契约与兼容性

- 公开契约必须围绕调用方需要完成的业务动作与结果设计，不能直接暴露内部模型、持久化形态或异常结构。
- 请求中缺省、空值、未知字段、边界值和无效组合必须有稳定含义，不能依赖框架偶然行为决定接受或拒绝。
- 成功、业务拒绝、认证失败、授权失败、资源冲突、暂态失败和内部错误必须具有结构化且可区分的语义。
- 列表、排序、过滤和分页必须产生稳定、可重复理解的结果，数据变化时的重复与遗漏风险不能被隐藏。
- 更新契约必须明确完整替换、部分改变和并发冲突的语义，后到请求不能默认获得静默覆盖权。
- 兼容性取决于字段含义、默认行为、约束和错误语义，而非只看数据形状；破坏性改变必须存在显式版本与过渡窗口。
- 契约中不得泄漏秘密、内部路径、堆栈和供应商细节，诊断需要与外部信息披露必须分离。

### 语义解释与确定性规则边界

- 实现业务判断前必须区分确定性规则与依赖上下文的语义解释；只有输入词汇、语法、映射和结果由当前权威完整枚举且具有稳定含义时，才可把判断实现为固定规则。
- 当含义取决于上下文、组合关系、表达差异或无法穷举的业务知识时，必须由产品明确的语义解释责任承担；应用层不得用业务关键词、句式正则、删词表或少量示例近似这一责任。
- 语义结果跨边界传递时应使用受约束的结构化契约，按用例表达已确认含义、适用范围、歧义、证据需求或下一步；缺失、无效和无法确定必须保持显式状态，不能回退到猜测。
- 确定性执行只负责结构与协议校验、权限和数据作用域、资源预算、幂等、去重、证据一致性及副作用控制；不得从格式命中、字段存在或局部文本进一步推导未经确认的业务含义。
- 证据不足、解释冲突或依赖失败时，应把当前事实、缺口和失败状态交回语义责任边界，以便重新解释、补充证据或请求澄清；静态启发式与预设处理顺序只能用于正式规则定义的封闭流程。
- 语义解释能力不可用时，降级必须显式、保守且可观察，并继续保持权限与事实性边界；不得以未经授权的启发式规则替代原有语义责任，也不得把无证据结论伪装为完成结果。
- 正则、枚举与固定映射可用于协议结构、标识符、格式、封闭词表及正式规则已经定义的确定性判断；测试必须同时覆盖等价表达、相邻但不同的含义及边界失败，单个示例或私有调用顺序不能证明通用语义行为。

### 信任校验与错误语义

- 每个外来值都必须按来源判断可信度，身份、租户、权限、价格和审计主体不能因客户端提供便成为权威事实。
- 结构与格式问题应在系统边缘拒绝，业务资格和状态规则应在共享业务边界执行，不能让单一入口承担全部校验。
- 规范化必须具有确定语义，并与唯一性、签名、授权和持久化判断保持一致，不能在不同入口产生不同等价值。
- 错误分类应由失败性质和可恢复动作决定，不能通过捕获全部异常、静默吞错或统一成功响应掩盖根因。
- 对外错误必须稳定且避免扩大信息泄漏，对内诊断必须保留关联与根因；安全裁剪不等于删除所有可诊断差异。
- 校验失败不得产生未声明副作用，错误处理本身也不能泄漏敏感数据或改变原业务状态。
