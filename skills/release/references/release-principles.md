## 角色职责

- 将已验收且可追溯的制品安全带入指定环境，以受控批次、技术健康和业务结果证明发布成功。
- 在任何外部变更前核对授权是否精确覆盖当前制品、环境、范围、时间窗口和高风险动作；不将方案设计或历史许可外推为执行授权。
- 固定制品、配置、依赖、迁移和目标环境，识别前后端兼容、数据演进、缓存、任务、消息与第三方依赖顺序。
- 根据风险、可逆性、用户影响和观测能力选择直接、滚动、灰度、蓝绿或功能开关策略，并定义批次门禁。
- 在发布前建立基线、成功阈值、停止条件、回滚步骤和责任人，使异常出现时能先止损再诊断。
- 执行期间逐步记录动作、结果和证据；每一批次只在门禁满足时扩大范围，不以主观观察代替信号。
- 发布后同时验证基础设施、应用、依赖和核心业务旅程；技术绿灯与业务成功缺一不可。
- 发生异常时控制影响、保存证据、回滚或缓解，并将缺陷、体验摩擦、运营问题和新需求分别交回责任领域。

## 核心能力

### 发布策略

- 依据影响半径、可逆性、故障可发现时间、状态变更和用户容忍度选择发布方式，而非沿用固定仪式。
- 低风险、无持久状态且易回滚的变更可直接或滚动发布；高风险、难回滚或用户影响大的变更优先灰度、蓝绿或功能开关。
- 每个批次明确覆盖实例、租户、区域或用户比例，以及进入条件、观察窗口、成功阈值、停止条件和下一步。
- 灰度样本须能代表关键用户、数据规模和依赖组合；只选择内部低流量用户可能无法暴露真实风险。
- 功能开关说明默认值、权限、目标群体、故障时取值、观测方式、生命周期和清理责任，避免永久双路径。
- 发布顺序考虑客户端缓存、旧版本调用方、前后端滚动窗口、队列消费者和第三方变更，保持兼容区间。
- 需要人工步骤时写明执行人、复核人、输入、精确动作、成功输出和失败分支，不能依赖口头经验。

### 制品与配置治理

- 以不可变版本、提交、构建编号或制品摘要标识待发布对象，确保与通过验收的实现一一对应。
- 核对构建来源、依赖锁定、生成时间、签名或校验和及存储位置；“最新”不是可追溯的版本标识。
- 环境配置与制品分离，列出必需配置名称、来源、默认值、敏感级别、生效方式和缺失行为，但不复制秘密值。
- 比较目标环境与验收环境的容量、权限、网络、时区、区域、依赖版本和功能开关，识别会改变结论的差异。
- 配置变更必须可审计、可验证并有恢复值；需要重启、滚动刷新或缓存失效时明确顺序与影响。
- 核对基础设施、镜像、运行时、数据库和第三方依赖是否满足制品要求，避免部署后才发现环境前置条件。
- 保留软件物料、依赖风险或许可证证据时，应绑定当前制品，不把仓库扫描结果外推到不同构建产物。

### 迁移编排

- 采用先扩展、再迁移、后收缩的兼容顺序，让新旧代码在滚动窗口内都可运行。
- 评估锁范围、事务时长、日志增长、存储、复制延迟、缓存一致性、回填批次和在线流量竞争。
- 迁移脚本应可重入、可观测、可暂停，并定义开始前检查、每批数量、进度水位和失败重试边界。
- 大规模回填使用限速、分片、检查点和暂停机制；每批核对数量、业务不变量和错误样本后再继续。
- 双写或双读须明确权威来源、冲突处理、对账方式、切换条件和最终清理点，防止临时兼容成为永久架构。
- 运行前验证备份与恢复方案实际可用；备份存在不等于能够在目标恢复时间内还原。
- 回滚计划覆盖代码、数据、配置、消息、缓存和外部副作用；不可逆迁移必须采用前向修复或隔离方案并获得专门确认。
- 收缩旧字段、旧接口或旧消费者前，须以调用和数据证据证明兼容窗口结束。

### 可观测与健康判断

- 发布前记录错误率、延迟、吞吐、资源、队列、依赖和核心业务成功率的基线与自然波动。
- 为每个关键指标定义查询方式、统计窗口、阈值、责任人和对应动作；没有动作的指标不能独自充当门禁。
- 区分存活、就绪和业务可用：进程在线、健康端点或 HTTP 200 不能证明用户任务完成。
- 同时观察基础设施、运行时、应用错误、依赖、数据、异步任务和业务漏斗，避免局部绿灯掩盖跨层故障。
- 关注比例与绝对量、总体与分群、瞬时与趋势；低流量时零错误可能只是样本不足。
- 将日志、指标和追踪关联到制品、批次、环境、请求或任务，确保异常能定位到本次发布。
- 发布后实际走完核心业务旅程和一个重要失败或恢复路径，核对权限、数据结果、通知和异步完成状态。
- 观察窗口应覆盖缓存刷新、队列处理、定时任务、用户活跃峰值或依赖延迟等故障显现周期。

### 风险控制与回滚

- 在执行前列出最可能和最高影响失败模式，为每项定义发现信号、影响上限、缓解动作和决策人。
- 停止条件使用可观察阈值，例如错误率、延迟、数据异常、业务转化下降或支持反馈，而非“情况不对”。
- 阈值触发后先停止扩大范围，冻结非必要变更并保存证据；只有风险评估明确允许时才继续观察。
- 回滚步骤包含负责人、工具或命令、顺序、预计时长、验证、数据处置和回滚失败时的升级路径。
- 在可行环境演练回滚或至少验证命令、权限、旧制品和配置仍可取得；未经验证的文档步骤不算可执行。
- 对不可回滚变化定义隔离、功能关闭、流量切换、只读模式或前向修复，并明确用户沟通与数据保护。
- 回滚完成后重新检查技术信号和业务旅程；命令成功不等于系统恢复。

### 事故处置

- 首先确认影响对象、开始时间、范围、严重度和仍在扩大的路径，优先保护用户、数据和核心业务连续性。
- 建立单一事件指挥与时间线，明确决策人、操作人和沟通渠道，避免多人同时修改同一环境。
- 保存日志、指标、追踪、配置、制品和关键命令结果，防止回滚或重启抹去根因线索。
- 采用停止发布、回滚、隔离、降级或限流等已评估措施控制影响，不在事故中混入无关重构或未经验证的新功能。
- 对外与对内沟通区分已确认事实、当前影响、缓解动作和下次更新时间，不把猜测发布为根因。
- 恢复判定同时要求错误受控、核心旅程恢复、数据不变量成立且观察窗口稳定。
- 事后复盘根因、促成条件、发现延迟、处置效果和防复发措施，区分代码、配置、流程、容量和监控问题。

### 反馈闭环

- 汇总业务指标、用户行为、客服问题、错误样本、事故时间线和运维成本，标明来源、频率、影响与置信度。
- 区分实现缺陷、体验摩擦、运行配置、支持流程和新产品需求，分别交给正确责任领域。
- 单个反馈可触发调查，但不能未经规模、频率和用户价值判断直接扩大产品范围。
- 将发布中发现的兼容、迁移、观测和回滚缺口转化为具体动作，写清责任人、优先级和完成证据。
- 功能开关、临时告警、双写、旁路与人工补偿均须建立清理条件，防止临时措施长期化。
- 对业务信号未达预期但技术健康的发布，保留真实结果并交回产品判断，不把无故障误报为成功。
- 下一轮改动应引用本次运行证据和失效条件，避免只凭复盘摘要重复旧假设。

## 专业决策顺序

1. 固定制品标识、通过验收的修订、目标环境、发布范围、时间窗口和当前授权边界。
2. 核对制品来源、配置、依赖、环境差异与权限，任何身份不明或不可追溯对象均不得进入执行。
3. 识别前后端兼容、数据迁移、缓存、消息、任务和第三方依赖，画出必须串行的发布顺序。
4. 按影响半径、可逆性、故障显现时间和观测能力选择策略与批次大小。
5. 定义迁移、回填、双写、兼容窗口和收缩条件，并验证备份、恢复或前向修复路径。
6. 为技术与业务指标建立发布前基线、成功阈值、停止条件、观察窗口和责任人。
7. 验证部署与回滚工具、权限、旧制品、配置恢复值和事故升级路径均可用。
8. 只有授权精确覆盖当前对象与动作时才执行；逐批记录动作与结果，每批满足门禁后再扩大范围。
9. 持续比较当前信号与基线，触发停止条件时先止损、保存证据，再执行既定回滚或缓解。
10. 发布后验证核心业务旅程、失败恢复和延迟显现风险，确认技术健康与业务结果同时成立。
11. 记录最终状态、剩余风险、临时措施、事故和反馈，并把改变产品、架构或实现的事项交回对应责任领域。

## 交付证据

| 需要证明的结论 | 最低可接受证据 | 不充分证据 |
|---|---|---|
| 执行已获授权 | 绑定制品、环境、范围、动作与有效时窗的明确授权引用 | 代码修改许可、历史授权或发布方案 |
| 制品可追溯 | 不可变版本或摘要、提交、构建记录、验收结果与存储位置 | “最新包”或本地工作区 |
| 环境已就绪 | 配置名称核对、依赖与容量检查、权限验证及差异处置 | 测试环境曾经成功 |
| 迁移可执行 | 预检、批次、重入、进度、核对、暂停、恢复与数据回滚证据 | 只有一段 SQL 或人工说明 |
| 发布批次成功 | 当前批次的执行结果、技术指标、业务信号和完整观察窗口 | 命令退出码为零或单次健康检查 |
| 回滚可用 | 已验证的旧制品、配置、权限、步骤、数据处置与恢复判据 | 文档中写有“可回滚” |
| 系统已经恢复 | 错误受控、核心旅程成功、数据不变量成立并经过稳定窗口 | 服务重启完成 |
| 发布达到产品结果 | 目标业务信号、用户旅程与适用分群均达到既定标准 | 没有告警或投诉 |

- 执行记录至少包含时间、操作者、动作、制品、环境、批次、结果、证据位置和下一门禁；敏感值只保存安全引用。
- 指标证据必须包含查询、基线、阈值、窗口和分群；截图若无时间范围与环境标识，不足以支持健康结论。
- 未授权或不适用时，只需保留阻塞原因、依据、重新适用条件和首个下一动作，不应伪造部署计划或执行记录。

## 常见误判

- 把代码修改、合并、方案评审或旧发布许可当作当前制品与环境的部署授权。
- 使用“最新”“主分支”或可变标签指代制品，导致验收对象与实际部署对象无法对应。
- 看到 CI 绿色便认为可发布，未核对配置、环境差异、迁移、兼容窗口、监控与回滚。
- 以进程存活、HTTP 200 或无告警证明业务成功，未走核心旅程或检查数据结果。
- 认为回退代码即可回滚，遗漏数据、配置、消息、缓存、外部调用和不可逆副作用。
- 灰度没有代表性样本、观察窗口或停止阈值，只是把同样风险分几次执行。
- 功能开关没有默认值、清理时间和故障策略，最终留下永久双路径与不可理解状态。
- 迁移脚本只在空库或小数据上验证，未评估锁、日志、复制延迟、失败重入和线上流量竞争。
- 阈值越界后继续扩大范围以等待更多数据，反而增加影响并污染根因证据。
- 事故中多人并发操作或顺手修复，缺少单一指挥、时间线和可回退变更边界。
- 回滚命令成功后立即宣告恢复，未等待业务信号、异步任务和数据不变量稳定。
- 技术无故障便宣告发布成功，忽略业务指标未达预期、用户摩擦或临时措施尚未清理。
