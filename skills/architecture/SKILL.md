# 系统架构设计

只处理当前需求真正存在的跨边界缺口，使系统边界、责任和失败行为在编码前明确；普通局部实现不得因抽象的“可扩展性”升级成架构工程，也不得擅自进入后端或前端代码实现。

## 输入门禁

- 明确 Git 仓库根、当前产品与稳定的 `product-id`、相关项目根、仓库指令、用户结果、业务规则、变更范围、调用方、验收标准和不得破坏的行为。
- 读取相关产品事实、存在时的 `docs/product-studio/<product-id>/architecture.md` 中命中的总结性代码事实，以及现有模块、进程、存储、数据所有者、上下游、协议、部署单元、信任边界和运行信号。
- 产品用户、旅程、业务闭环、规则、范围或体验取舍未定时交给 `$design`；具体 API 字段、Schema、事务与服务端代码交给 `$backend`；页面、组件和浏览器行为交给 `$frontend`。
- 同时牵涉多个实现技能或共享契约时，由 `$router` 选择最小技能链；只有系统架构分析时可停在架构结论，不得擅自进入代码实现。

## 专业能力

先查看 [系统架构能力准则](references/principles.md) 的“目录”与“核心能力”，完整读取本次命中的能力段落；形成完整架构决定、比较方案或复核风险时，再读“常见误判”。

## 架构流程

1. 从用户可见结果追踪入口、模块、进程、权威数据、外部依赖、部署单元和副作用，区分已核验事实、假设和未知。
2. 判断缺口是否真正跨越模块、进程、数据所有权、信任边界或部署单元；不跨边界的局部选择退回对应实现技能。
3. 完整读取本次命中的能力准则，以当前证据和真实消费者形成必要的架构决定；未受影响的能力不机械展开，具体字段、Schema、事务和代码仍交给实现技能。
4. 比较包含沿用现状和局部修补在内的最小候选方案，记录选择、放弃项、代价、可逆性、验证办法和重审触发。
5. 将采用的决定拆成可独立实现与验证的切片，明确前置决定、责任技能、影响边界、消费者、验证信号和失败收口。
6. 实现阶段出现足以改变边界、所有权、共享不变量、跨边界语义或质量决定的新证据时，只退回受影响的架构决定，并重新核对其消费者与验证门禁。

## 当前产品事实记忆

开始工作时，先从用户范围、仓库原生产品身份、产品入口与元数据、相关项目根、目标代码与调用链确定 Git 仓库根及仓库内唯一、稳定且可安全作为单级目录名的 `product-id`；优先复用已确认属于同一产品的既有事实目录，不从任一项目目录名机械推导。同一 Git 仓库包含多个产品时，只处理本轮命中的产品。若 `<Git仓库根>/docs/product-studio/<product-id>/architecture.md` 存在，只读取命中的事实主题及直接关联。获准写入的实现、验收或明确记忆维护任务收口前完整读取 [architecture 记忆规则与实例格式](references/memory.md)，以本次实际核验的当前代码、配置、契约和验证结果为本轮增量范围，仅同步 `architecture` 自己的当前事实；事实册整体是 `architecture` 对该产品的累计专业事实视图，不受本轮范围限制，事实是否在本次被修改不影响收录，最终差异不构成事实边界。首次确有事实时在已确认的产品记忆目录创建同名事实册，不得预建产品记忆目录或空册；跨产品任务逐产品同步对应事实册，不把不同产品事实合并，产品归属无法唯一确定时不创建事实目录并报告歧义。纯架构方案及重构、迁移和变更过程不入册。只读任务未获事实册写入授权时只报告候选事实；完成当前范围核对后无增、改、删则报告 `memory: 0 facts changed`。

产品归属或 `product-id` 无法唯一确定时，不把任何候选事实册作为当前产品事实读取或写入，也不创建目录，并报告歧义。

## 输出与交接

- 交付架构问题与系统上下文、边界职责、数据所有权与共享不变量、跨边界交互语义、质量方案决定、故障与恢复约束、安全与信任约束、可观测与可运行约束、演进条件、实现切片和验证办法。
- 向 `$backend` 交付须落实的操作语义、责任边界、兼容要求、故障行为与实现切片；后端负责具体 API、Schema、事务和服务端代码，不得暗改架构决定。
- 向 `$frontend` 交付影响用户可见状态、权限、异步进度、降级和恢复的系统约束；向 `$verification` 交付风险场景、证据入口和重审条件。
- 实现发现新证据足以改变所有权、共享不变量、跨边界语义或质量约束时，退回本技能裁决，不在下游建立第二套架构。

## 完成门禁

- 架构问题有当前跨边界证据，沿用现状或局部实现不足以安全收口；未受影响的能力没有被机械展开。
- 每项关键共享不变量有唯一责任边界、执行位置、违规表现、恢复动作和验证信号。
- 跨边界交互具有消费者、正常与失败语义、权限与兼容责任；实现角色无需猜测系统边界。
- 候选方案包含沿用现状或局部修补，采用理由、代价、可逆性与重审条件明确。
- 适用的超时、重复、乱序、部分成功、依赖故障、安全滥用、迁移和回滚状态均有收敛路径。
- 架构结论绑定当前代码、Schema、部署拓扑或运行证据，并已拆成有消费者和验证信号的切片；外部案例和模式名称未冒充当前事实。

## 边界

- 可裁定系统与领域边界、数据主权、共享不变量、跨边界交互语义、质量属性、信任边界、一致性目标、故障恢复、运行约束和演进方案。
- 不自行改变目标用户、产品范围、用户旅程、业务规则或体验目标；这些交给 `$design`。
- 不代替 `$backend` 决定具体接口字段、错误码、表结构、事务代码和服务端实现，不代替 `$frontend` 决定组件、视觉与浏览器交互。
- 可设计迁移、回填、灰度与回滚方案，但不执行环境迁移、生产数据修复、切流或其他外部状态变更。
- 不代替 `$verification` 宣告产品增量通过；静态设计未取得真实实现与运行证据时，只能报告设计结论及待验证项。
