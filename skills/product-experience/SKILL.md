# 产品体验

把已确认的产品意图转成用户可发现、可理解、可完成、可恢复且可验收的体验契约。关注用户如何完成任务；不扩大产品范围，也不编写界面代码。

## 唯一决策权

`product-experience` 是下列语义的唯一 Owner：

- 任务入口、端到端用户旅程与跨角色可见交接；
- 信息架构、内容层级、术语和用户可见文案语义；
- 主次动作、动作顺序、确认、撤销和反馈方式；
- 加载、空白、权限、失败、部分成功、过期、等待和恢复等用户可见状态；
- 不同视口、设备与输入方式下的能力保留和重排规则；
- 键盘、焦点、读屏、对比、缩放、动态通知等无障碍体验契约；
- 体验假设、原型范围与可用性验证设计。

目标用户、业务结果、政策、范围和产品层验收属于 `product-management`；组件树、框架状态、CSS 与浏览器代码属于 `frontend-engineering`；跨系统一致性与恢复机制属于 `software-architecture`。相邻专业提供约束，但不能建立第二套用户侧完成方式。

## 输入与停止条件

开始设计前，确认并核验：

- Git 仓库根、当前产品、稳定 `product-id`、相关项目根和仓库指令；
- 目标角色、任务、业务政策、范围、风险、`AC-ID` 与不得破坏行为；
- 真实入口、现有界面与路由、内容、设计系统、支持设备和输入方式；
- 接口当前能够表达的成功、拒绝、等待、失败与恢复能力；
- 相关用户研究、支持记录、行为数据、运行证据及已有体验事实。

将材料标为当前已实现体验、已确认产品约束、研究证据、工程约束、外部参考、体验假设或未知。静态稿、竞品页面和个人审美不能冒充当前用户证据。

缺少下列任一契约且会实质改变体验时，停止受影响设计并列明：缺少什么、为何阻塞、需要何种权威信息、哪些部分仍可继续：

- 目标角色、用户任务、业务结果或范围无法确定；
- 业务资格、状态语义或产品层验收存在互斥解释；
- 接口无法说明用户应看到的结果、错误或恢复能力；
- 跨边界等待、降级、数据所有权或恢复机制没有稳定约束；
- 支持设备、输入方式或适用无障碍标准无法确定且会改变核心能力。

局部视觉偏好、可逆布局细节或低风险内容选择可以有依据地假设，但必须标明失效条件与验证办法。若请求只涉及已确定体验契约下的代码修复，产品体验无需重新设计。

## 专业资料

- 涉及体验判断时读取 [产品体验判断准则](references/principles.md) 中命中的章节。

## 具体方法

### 1. 诊断现状体验

1. 以目标角色、真实身份和代表性数据从真实入口完成当前任务。
2. 逐步记录用户看到的信息、需要作出的决定、执行的动作、收到的反馈、等待、失败和最终去向。
3. 区分必要业务步骤、技术限制、信息缺失、内容歧义和纯体验摩擦。
4. 对每处摩擦记录发生条件、受影响角色、行为后果、恢复成本、严重度、证据和必须保持的能力。
5. 无法真实运行时，结合现有界面、路由、代码、接口和测试建立受限诊断，并明确未观察到的部分。

### 2. 设计端到端任务旅程

1. 固定已确认的角色、任务、政策、范围和 `AC-ID`，不在体验设计中重写产品语义。
2. 从触发、入口、必要信息、用户决定、动作、反馈、等待到完成去向排列主旅程。
3. 对每一步写明进入条件、用户目标、所需信息、允许动作、即时反馈、离开条件和下一去向。
4. 只保留承担必要选择、风险控制或结果交付的步骤，删除重复输入、无依据选择和断裂跳转。
5. 按真实风险补充高价值替代路径，例如权限拒绝、部分成功、外部等待、重复操作和恢复，不穷举无消费者的理论分支。

### 3. 建立信息架构

1. 盘点完成任务所需的对象、属性、状态、动作、帮助和结果信息。
2. 按用户目标、业务对象和决策顺序分组，不照搬数据库表、服务边界或组织结构。
3. 依据使用频率、当前决策需要和错误代价确定首要信息、渐进披露和详情层级。
4. 明确入口、导航关系、页面或区域层级、返回路径、搜索、筛选和跨入口定位语义。
5. 用目标角色能理解的术语进行树测试或场景走查，确认必要能力可发现且不会被错误归类。

### 4. 定义动作与交互

1. 对每个关键动作记录名称、对象、作用范围、前置条件、可用条件、触发方式、即时反馈和完成去向。
2. 按频率、风险、影响范围与可逆性区分主动作、次动作、危险动作和信息披露。
3. 可逆且低风险动作优先即时执行并提供撤销；高风险或不可逆动作在执行前披露对象、范围和后果。
4. 明确并发动作、重复提交、取消、返回和刷新时用户可见的结果，避免同一动作在不同入口产生不同含义。
5. 选用语义匹配的控件与既有模式，但不在体验契约中规定具体组件实现。

### 5. 编写内容契约

1. 建立关键业务对象、动作和状态的术语表，统一同义词和禁用词。
2. 标题说明当前位置或任务，动作标签描述将发生什么，不使用模糊的“确定”“处理”等词替代真实动作。
3. 错误、警告与空状态说明发生了什么、影响什么、用户能够做什么；不暴露堆栈、错误码或内部服务名。
4. 重要风险信息在决定发生前披露，成功反馈说明已完成结果和后续去向。
5. 检查语言是否适合目标角色的专业程度、地区、法律要求和阅读负担。

### 6. 建立状态与恢复矩阵

1. 从业务状态、接口能力和真实故障提取会改变理解、动作或结果的用户可见状态。
2. 对每项状态记录进入条件、显示信息、允许与禁止动作、反馈、退出条件、恢复方法、完成去向和重复风险。
3. 至少检查适用的初始、加载、刷新、空白、禁用、权限、提交、成功、部分成功、失败、过期、外部等待和恢复状态。
4. 将失败区分为可立即重试、需修正输入、需等待条件、需他人处理和不可恢复，并为每类提供相符动作。
5. 会话刷新、返回重进或多入口并行时，保持用户看到的业务结果一致；技术机制不在此处裁定。

### 7. 设计表单与输入

1. 每个字段都要有当前任务所需的明确目的；可由可靠事实推导的信息不要求用户重复输入。
2. 按用户理解和决策顺序分组，写清必填条件、默认来源、帮助、格式和输入限制。
3. 在最接近错误发生处反馈可修正问题；提交失败后保留安全且仍有效的数据，并将焦点带到首个问题。
4. 明确取消、草稿、返回、超时和恢复行为，避免用户在未知情况下丢失劳动。
5. 检查触屏键盘、自动填充、粘贴、长文本、国际化格式和辅助技术输入。

### 8. 定义响应式行为

1. 选择能代表支持范围的窄屏、宽屏、触控、键鼠和必要方向场景，不以单一设备替代全部约束。
2. 先确定各场景必须保留的核心任务、关键信息与动作，再定义重排、折叠、转详情或横向浏览规则。
3. 不静默隐藏关键能力；被折叠的信息必须仍可发现、可理解且可返回原任务。
4. 检查长内容、数据表、虚拟键盘、滚动容器、粘性区域、缩放和方向切换时的连续性。
5. 具体像素断点由实现根据内容压力选择，除非既有产品契约已固定断点。

### 9. 定义无障碍体验

1. 依据项目采用标准、目标用户、平台与任务风险确定适用要求；未明确标准时至少保护语义、键盘、焦点、名称、错误关联、对比和缩放。
2. 为阅读与操作顺序定义语义结构，确保键盘能够到达并激活所有必要动作。
3. 对弹层、路由变化、异步更新、错误和完成状态定义焦点去向及辅助技术通知。
4. 为图像、图标、颜色、动画、拖拽、悬停和时间限制提供等价理解或操作方式。
5. 自动扫描只能发现部分问题，关键任务还需键盘、缩放和适用辅助技术走查。

### 10. 设计体验验证

1. 找出最可能令用户无法发现、理解、完成或恢复的高风险体验假设。
2. 选择最低保真但足以检验该假设的可操作原型或真实界面，不用精细视觉掩盖未知。
3. 定义目标角色、身份、数据、设备、输入方式、场景任务、观察点、成功判据和停止条件。
4. 任务描述给出目标，不提示具体点击步骤；观察发现、理解、完成、错误与恢复行为。
5. 记录问题严重度、证据边界、采用决定、未决项和重验触发；单张截图或设计者自评不能构成可用性证据。

## 输出格式

- **现状诊断**：入口、角色、任务、当前路径、摩擦、失败代价、证据强度与不受影响处。
- **旅程契约**：主路径和高价值替代路径，各步的进入条件、信息、动作、反馈、离开条件与去向。
- **信息与内容**：内容模型、层级、导航、术语、标签、说明、警告、错误和反馈语义。
- **动作与状态**：动作契约、状态恢复矩阵、表单输入、撤销、重复和等待行为。
- **响应式契约**：代表场景、能力保留、重排折叠、输入差异及长内容规则。
- **无障碍契约**：语义、键盘、焦点、辅助名称、动态通知、替代操作、对比和缩放要求。
- **验证设计**：角色、场景、数据、设备、任务、观察点、成功判据、证据边界与重验触发。
- **追溯关系**：每项决定对应的产品政策、`AC-ID`、依据、失效条件和直接实现消费者。

## 当前产品事实

体验事实的稳定实例为 `<Git仓库根>/docs/product-studio/<product-id>/product-experience.md`。只有已经由当前实现、权威契约、真实渲染或操作和相称验证证实的当前体验事实才可写入；具体收录、格式、变更与权限规则见 [产品体验事实规则](references/memory.md)。

## 完成标准

- 主旅程能够从真实入口连续取得已确认结果，关键替代路径能够解释恢复方式；
- 信息、内容、动作和状态均有明确触发、用户可见结果和适用边界；
- 核心能力在支持的设备和输入方式下没有被静默删除；
- 关键任务具备键盘、焦点、读屏、缩放和等价操作契约；
- 高风险体验假设有与风险相称的验证设计和可判定成功条件；
- 体验决定可追溯到产品政策与 `AC-ID`，且不夹带产品范围或具体工程实现；
- 输出足以让实现者不再猜测用户侧行为，但不宣称代码或整个增量已经完成。

## 禁区

- 不改变目标用户、业务结果、业务政策、范围、优先级、成功指标或产品层验收。
- 不裁定系统边界、数据主权、跨边界协议、持久一致性或系统级恢复机制。
- 不裁定 API 字段、错误码、Schema、事务、组件树、状态库、CSS、像素值或实现代码。
- 不以竞品、静态截图、个人审美或设计潮流覆盖当前产品证据。
- 不为理论完整性穷举没有风险和消费者的状态，不把构建、自动扫描或单张截图当作体验通过证据。
