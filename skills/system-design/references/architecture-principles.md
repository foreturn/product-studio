# 架构设计能力准则

## 系统上下文与领域边界

- 从用户旅程和业务能力识别系统职责、外部参与者、信任边界与上下游，不从现有目录机械推导架构。
- 为每类核心数据指定唯一权威来源和生命周期责任，避免多个模块都能任意修改同一事实。
- 模块按稳定业务职责聚合，接口只暴露消费者真正需要的行为；避免跨层读取内部表或共享可变状态。
- 让目录、命名和依赖方向表达边界，防止通用工具夹带特定业务规则。
- 产品范围变化退回产品角色，不用架构方案反向偷改用户旅程或验收标准。
- 聚合与限界上下文按“同一业务不变量、同步一致性需求、生命周期同步”划分，而非按表或 CRUD 切分边界。

## 数据流与契约

- 画清请求、事件、批处理和数据同步的方向、触发者、所有者、延迟预期与失败返回路径。
- 明确同步或异步选择的业务理由；需要即时一致结果时不要仅为“解耦”改成消息最终一致。
- 契约定义输入、输出、不变量、错误、超时、幂等、顺序、版本和兼容责任。
- 禁止循环依赖和跨边界隐式写入；共享能力通过稳定接口或明确事件传播。
- 为关键契约指定消费者及验证方式，没有消费者的扩展点不进入当前设计。

## 质量属性与容量

- 根据真实用户量、数据量、请求峰值、延迟目标、恢复目标和成本约束评估方案，不凭空设计互联网规模。
- 识别关键路径与可降级路径，明确哪些操作必须强一致、低延迟或高可用，哪些可以延后处理。
- 性能讨论落到查询次数、数据规模、序列化、网络往返、锁竞争、缓存命中和资源上限。
- 可扩展性优先通过无状态、分区边界、批处理和异步化解决，但只在当前证据表明需要时引入。
- 维护性包含可读性、测试隔离、替换成本、运行排障和团队熟悉度，不只看代码行数。

## 故障、一致性与恢复

- 列出依赖超时、网络中断、重复、乱序、进程重启、部分成功、容量耗尽和数据损坏等适用故障。
- 对每个状态变化说明事务边界、幂等键、重试责任、补偿动作和最终可观察结果。
- 重试必须有上限、退避和去重；不可恢复错误要快速失败，可恢复错误要保留上下文。
- 缓存必须说明权威数据、失效条件、陈旧容忍和故障时行为，不把缓存当第二事实源。
- 恢复设计包含数据校验、人工处置入口、回放或补偿能力，而不只描述服务重启。
- 一致性模型按场景选择：资金、库存、权限等用强一致（事务/锁）；跨服务、跨库、可容忍短暂不一致的用最终一致（事件/补偿），并说明收敛时延与补偿成本。

## 安全与隐私

- 识别身份边界、授权决策点、敏感字段、密钥、外部输入和审计事件。
- 采用最小权限、默认拒绝、服务端鉴权和数据范围校验；客户端隐藏不能充当权限控制。
- 对输入进行长度、格式、类型和业务约束校验，考虑注入、越权、重放和敏感信息泄露。
- 明确数据加密、脱敏、保留、删除、备份和访问审计要求；没有需求时不虚构合规结论。
- 威胁建模按 STRIDE 思路逐项核查：伪装（认证）、篡改（完整性）、抵赖（审计）、信息泄露（最小化/加密）、拒绝服务（限流/隔离）、越权（授权）。

## 可观测性与运行

- 为核心旅程设计业务成功、失败和延迟信号，为关键依赖设计技术健康信号。
- 日志包含可关联标识、阶段、结果和可行动上下文，不记录密钥、令牌或不必要的个人数据。
- 指标和告警对应用户影响与处置动作；没有行动含义的高噪声告警应删除或降级。
- 追踪跨模块请求和异步任务的传播，使超时、排队与部分失败能够定位责任边界。

## 演进与架构决策

- 比较至少一个更简单方案，说明采用方案为何值得其复杂度。
- 决策记录包含背景、约束、候选、选择、代价、可逆性、迁移、回滚、验证和重审条件。
- 迁移采用兼容优先的顺序，使新旧代码和数据在过渡期可共存；避免一次性大爆炸切换。
- 遵循 YAGNI 与 KISS，不为假设中的租户、规模、供应商或扩展场景预设框架。
- 只有重复逻辑形成稳定共性时才抽象；若必须依赖大量注释理解设计，先降低复杂度。
